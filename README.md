# 🍚 한끼바꿈 — 서비스 기획서

> 대학생의 재능과 소상공인의 위기 극복을 잇는 **현금 없는 로컬 상생 플랫폼**
>

## 1. 개요

| 항목 | 내용 |
| --- | --- |
| 서비스명 | 한끼바꿈 |
| 한 줄 정의 | 학생의 디지털 재능(마케팅·디자인)과 사장님의 식사권을 물물교환하는 로컬 상생 플랫폼 |

## 2. 문제 정의

### 2-1. 소상공인 (동네 식당 사장님)

- 마케팅 **비용과 스킬이 모두 부족**하다 — 포스터, SNS, 리뷰 관리를 할 여력이 없다
- 노쇼·우천 같은 **돌발 상황에 대응할 홍보 채널이 없다**
- 마감 시간대 **남는 재고를 처리할 방법이 없다**

### 2-2. 대학생

- **식비 부담**이 크다
- 전공·관심사(디자인, 영상, SNS 운영)를 실무에 적용해 볼 **포트폴리오 기회가 부족**하다

### 2-3. 핵심 통찰

두 집단이 가진 것과 필요한 것이 정확히 **교차**한다. 학생은 시간과 디지털 스킬이 있고 밥이 필요하며, 사장님은 밥이 있고 디지털 스킬이 필요하다. 돈이 오가지 않아도 교환이 성립한다.

## 3. 솔루션: 핵심 기능

### 3-1. Tab 2 — 로컬 재능 헬퍼 ⭐ (핵심 · 리소스 60~70%)

학생의 디지털 스킬과 사장님의 식사권을 물물교환하는 **본 서비스의 진짜 차별점**.

**거래 플로우**

```
요청 등록 → 매칭 → 작업 수행 → 완료 인증(결과물 업로드)
→ 양측 완료 확인 → 식사권 지급 → 상호 평점
```

**요청 게시글 필수 필드 (분쟁 예방 규칙 내장)**

| 필드 | 설명 | 목적 |
| --- | --- | --- |
| 작업 태그 | #포스터제작 등 (아래 8절 참조) | 분류·매칭 |
| 기대 결과물 예시/수준 | 참고 이미지 또는 설명 첨부 **필수** | 기대치 차이로 인한 분쟁 예방 |
| 수정 요청 범위 | "수정 요청 1회 포함" 기본 명시 | 무한 수정 요구 차단 |
| 보상 | 식사권 수량 / 메뉴 (수량 스테퍼 + 시세 힌트) | 보상 명확화 |
| 완료 희망일 | 선택 입력 | 일정 기대치 조율 |
| 지역 | 프리셋 드롭다운 | 매칭 범위 |

### 3-2. Tab 1 — 동네 핫딜 (보조 · 리소스 30~40%)

마감 할인, 노쇼 발생, 우천 특가 등 **돌발 이벤트를 태그 기반으로 알리는** 게시판.

- **선순환 구조**: Tab 2에서 학생이 제작한 결과물 이미지가 Tab 1 게시글의 썸네일로 자동 재사용된다. 재능 교환의 결과물이 곧 홍보 자산이 되는 구조.
- **AI 보조 (9절)**: 사장님이 상황을 한 줄만 입력하면 홍보 문구와 태그가 자동 생성되어, "바쁜 사장님이 글을 올리지 않는" 문제를 완화한다.
- 운영 방향: MVP에서는 "Tab 2 완료 사례 쇼케이스 + 핫딜" 성격으로 가볍게 유지하는 방안을 검토 중.

## 4. 사용자 시나리오

### 시나리오 A. 사장님 — 재능 요청부터 식사권 지급까지 (Tab 2 핵심 플로우)

> **페르소나**: 김순자 (52) · 대학가 백반집 10년 차 · 손글씨 메뉴판을 코팅해 쓰는 중, SNS는 안 함
> 
1. 단골 학생에게 "메뉴판이 잘 안 보인다"는 말을 듣고 앱에서 **Tab 2 요청 등록**
2. 필수 필드 작성 — 태그 `#메뉴판디자인`, 참고하고 싶은 다른 가게 메뉴판 사진 첨부(기대치 명시), 보상 "백반 식사권 5장", 수정 1회 포함 확인, 지역 "○○대 앞" 선택
3. 디자인 전공 학생 2명이 지원 → 프로필과 평점을 보고 **매칭 수락** (상태값: `진행중`)
4. 3일 뒤 학생이 결과물 업로드 (상태값: `완료대기`) → 확인해 보니 가격 표기가 빠져 있어 **수정 1회 요청**
5. 수정본 재업로드 → 만족스러워서 **완료 확인 버튼** 클릭, 학생도 확인 → 상태값 `완료`, 식사권 5장 지급
6. 상호 평점 작성 (★5 "꼼꼼하고 빨라요") → **새 메뉴판 이미지가 Tab 1 핫딜 게시글의 썸네일로 자동 연동**

### 시나리오 B. 학생 — 밥값과 포트폴리오를 동시에 (Tab 2 수행자 관점)

> **페르소나**: 박지훈 (21) · 시각디자인과 2학년 · 자취생, 외주 경력 없음, 포트폴리오가 급함
> 
1. 학식이 지겹던 차에 앱에서 지역 프리셋 "○○대 앞"으로 **Tab 2 요청글 탐색**
2. `#메뉴판디자인` 요청 발견 — 기대 예시와 수정 범위(1회)가 명시돼 있어 **작업량을 예측하고 지원**
3. 매칭 후 작업, 결과물 업로드 → 수정 1회 반영 → 양측 완료 확인
4. **식사권 5장 획득** + 실제 가게에 걸린 첫 실무 결과물이 **포트폴리오로** 남음
5. 평점 ★5가 쌓여 다음 매칭에서 신뢰 자산이 됨

### 시나리오 C. 사장님 — 비 오는 날 한 줄로 핫딜 올리기 (Tab 1 + AI)

> **상황**: 수요일 저녁, 갑작스러운 비로 손님이 끊김. 김치찌개 재료는 오늘까지 써야 함
> 
1. Tab 1에서 글쓰기 → 한 줄 입력: **"비 와서 손님 없는데 김치찌개 남았어요"**
2. AI가 홍보 문구 + 태그 `#우천특가` `#당일한정` **자동 생성** → 사장님은 확인 버튼만 누름
3. 시나리오 A에서 만든 메뉴판 이미지가 썸네일로 자동 첨부
4. "○○대 앞" 프리셋을 등록한 학생들에게 알림 → 비 피해 근처에 있던 학생들이 방문

### 시나리오 D. 예외 — 노쇼 방지 자동취소

1. 학생이 Tab 2 요청에 지원해 매칭됐으나 **일정 시간 동안 응답 없음**
2. 시스템이 매칭을 **자동 취소**하고 요청글을 다시 모집 상태로 전환 → 사장님이 방치되지 않음

## 5. 화면 구조 (UI)

> 🔗 **프로토타입 연결**: 아래 6개 화면은 `동네식당SOS_프로토타입.html`에서 실제로 클릭하며 확인할 수 있다.
순수 HTML/CSS로 제작 (JS 없음) — 하단 탭·카드·버튼을 누르면 화면이 전환된다.
> 

### 5-1. 정보 구조 (IA)

```
한끼바꿈
├─ 상단 앱바: 로고 · 지역 프리셋 드롭다운(○○대 앞) · 알림 벨
├─ [탭] 🔥 동네 핫딜 (Tab 1)
│    ├─ ① 핫딜 피드 ─ 태그 필터 칩
│    └─ ② 핫딜 올리기 (AI 문구 생성)   ← 하단 중앙 ＋ 버튼
└─ [탭] 🤝 재능 헬퍼 (Tab 2)
     ├─ ③ 재능 피드 ─ 태그 필터 칩
     │    └─ ④ 요청 상세 (신뢰 장치 집합)
     │         └─ ⑤ 완료 · 상호 평점
     └─ ⑥ 요청 등록 폼 (사장님)
```

- 하단 내비게이션은 **탭 2개 + 중앙 글쓰기 버튼**으로 최소화 — 50대 사장님도 헤매지 않는 구조
- 지역은 화면 이동 없이 **앱바의 프리셋 드롭다운**에서 전환 (GPS·위치 API 미사용)

### 5-2. 화면 목록 & 구성 요소

| # | 화면 | 주요 UI 요소 | 대응 기획 요소 |
| --- | --- | --- | --- |
| ① | 핫딜 피드 | 태그 필터 칩, 핫딜 카드(마감 시각·남은 수량·도보 거리), **"재능헬퍼 결과물" 썸네일 배지** | 8절 태그 체계, 3-2절 선순환 구조 |
| ② | 핫딜 올리기 | 상황 한 줄 입력 → **AI 초안 카드**(문구+태그 자동), 결과물 사진 자동 첨부, "이대로 올리기 / 다시 만들기" | 9절 AI 활용, 리스크 4번 완화 |
| ③ | 재능 피드 | 태그 필터 칩, 요청 카드(상태 배지 `모집중·지원 n명`/`매칭완료`, 사장님 평점), **식권 티켓 컴포넌트** | 3-1절 물물교환, 상태값 운영 |
| ④ | 요청 상세 | **진행 스텝바**(요청등록→매칭→완료대기→완료·지급), 기대 결과물 예시 고정 노출, 수정 1회 룰박스, **양측 확인 버튼 2개** | 7절 신뢰·분쟁 장치 전체 |
| ⑤ | 완료·상호 평점 | 식사권 **"지급 완료" 티켓**, 별점+한줄후기, **포트폴리오 자동 저장 카드** | 7절 5항 상호평점, 리스크 1번 비금전 보상 |
| ⑥ | 요청 등록 폼 | 태그 선택 칩, 기대 예시 첨부(필수), 수정 1회 룰박스, 식사권 수량 스테퍼+**시세 힌트**, 완료 희망일, 지역 프리셋 | 3-1절 필수 필드 표의 화면 구현 |

### 5-3. 화면 흐름 (핵심 동선)

**사장님 동선** — 시나리오 A·C 대응

```
③ 재능 피드 → ⑥ 요청 등록 → (매칭·작업) → ④ 요청 상세에서 결과물 확인
→ 수정 1회 요청 → 완료 확인 → ⑤ 평점 작성
→ ② 핫딜 올리기 (한 줄 입력, 결과물 썸네일 자동 첨부) → ① 피드 게시
```

**학생(헬퍼) 동선** — 시나리오 B 대응

```
① 핫딜 피드 (밥 정보 소비) ↔ ③ 재능 피드 탐색 → ④ 상세에서 조건 확인 후 지원
→ 결과물 업로드 → 완료 확인 → ⑤ 식사권 수령 + 평점 + 포트폴리오 저장
```

- 두 동선이 ①에서 만난다: 학생을 매일 불러들이는 건 핫딜(밥)이고, 그 화면의 썸네일이 재능 교환의 결과물이다 — **선순환이 UI 동선 안에서 완성**된다.

### 5-4. 공통 UI 원칙

- **큰 글씨 · 큰 버튼 · 낮은 단계 수**: 주 사용자 한쪽이 50대 사장님 — 모든 핵심 행동은 화면당 버튼 1~2개로 제한
- **식권 티켓 = 시각 시그니처**: 보상이 등장하는 모든 지점(피드·상세·완료)에 절취선 티켓 컴포넌트로 일관 표기, 지급 완료 시 색상 전환(노랑→초록)
- **상태값이 채팅을 대체**: 스텝바·상태 배지가 "지금 어느 단계인지"를 항상 노출 — 실시간 채팅 없이 운영하는 스코프 원칙의 UI적 구현
- **AI는 초안까지만**: AI 생성물은 반드시 사장님 확인 버튼을 거쳐 게시 (자동 게시 없음)

## 6. 차별점 · 경쟁 서비스 비교

| 서비스 | 교환 축 | 재능 교환 | 완료인증 선순환 |
| --- | --- | --- | --- |
| 당근마켓 | 물건 ↔ 돈 | ✕ | ✕ |
| 라스트오더 | 마감 음식 ↔ 돈 | ✕ | ✕ |
| 배민 마감할인 | 음식 ↔ 돈 | ✕ | ✕ |
| 한끼바꿈 | **재능 ↔ 식사권** | **◯** | **◯ (결과물 → 홍보 썸네일)** |

기존 서비스는 전부 "물건/음식 ↔ 돈" 축이다. **"재능 물물교환 + 완료인증 선순환"은 비어 있는 독자 영역**이다.

## 7. 신뢰 · 분쟁 방지 장치

결제가 없는 구조이므로 신뢰 장치가 곧 서비스의 뼈대다. 새 기능 개발이 아니라 **상태값과 필드 설계에 규칙을 내장**하는 방식으로 구현한다.

1. **완료 인증** — 학생이 결과물을 업로드하면 상태값이 `진행중 → 완료대기`로 전환
2. **양측 확인** — 사장님과 학생 **모두 확인 버튼을 눌러야** `완료` 성립 (일방 완료 처리 불가)
3. **수정 1회 규칙** — 요청 등록 시 "수정 요청 1회 포함"이 기본 명시되어 무한 수정 분쟁 차단
4. **기대치 명시 의무** — 요청글에 기대 결과물 예시/수준 첨부 필수
5. **상호 평점** — 별점 + 한줄 후기 (양방향)
6. **노쇼 방지** — 일정 시간 응답이 없으면 자동 취소

## 9. AI 활용 방침

서비스 전체를 에이전트화하지 않는다. 기존 기획을 유지하되, 문제 정의와 자연스럽게 맞물리는 지점에 **경량 AI 기능 1개**를 얹는다.

- **기능**: 사장님이 상황을 한 줄 입력 (예: "비 오는데 손님 없고 김치찌개 남았어요") → LLM이 **홍보 문구 + 태그(#우천특가) 자동 생성** → 게시글 초안 완성
- **왜 이 지점인가**: 원래 문제 정의인 "사장님의 마케팅 스킬 부족"을 직접 해결하며, Tab 1의 약점(사장님이 글을 올릴 동기 부족)을 동시에 완화한다
- **구현 부담**: LLM API 호출 수준으로 낮음 — 4주 스코프에 안전하게 수용 가능
- ⚠️ **확인 필요**: 대회 요강의 AI Agent 정의(단순 LLM 호출 인정 여부, 멀티스텝/도구 사용 요구 여부)에 따라 설계 수위 조정

## 10. 리스크 분석 및 대응 (심사 Q&A 대비)

| # | 리스크 | 진단 | 대응 |

| 1 | **가치 교환 비대칭** — 재능 시장가(수만~수십만 원) ≫ 식사권 | 실서비스 6개월~1년 차에 학생 이탈로 나타나는 문제. 챌린지·파일럿 단계에서는 성립 | 초기 타겟을 **포트폴리오가 절실한 저학년**으로 설정. 확장안: 완료인증 결과물 기반 **학생 포트폴리오 페이지 자동 생성** 등 비금전 보상 (⑤ 화면에 반영) |
| 2 | **분쟁 중재 부재** — 결과물 퀄리티 이견, 식사권 미지급 | 결제 없는 구조의 최대 약점 | 7절의 규칙(수정 1회 · 양측 확인 · 기대치 명시)을 **필드 설계에 내장하여 해결** (④·⑥ 화면에 반영) |
| 3 | **콜드스타트** — 양면 플랫폼 + 좁은 지역 | 4주 내 "해결" 대상이 아니라 "계획 제시" 대상 | 파일럿 섭외 방식은 미확정 — 학교 앞 식당 직접 섭외 + 첫 거래 시딩 등 후보안 논의 중 |
| 4 | **Tab 1 참여 동기 부족** — 바쁜 사장님이 글을 안 올림 | 수동 게시 의존 구조의 한계 | 9절 **AI 문구 자동 생성**으로 게시 비용을 "한 줄 입력"으로 축소 (② 화면에 반영). Tab 1 리소스 추가 축소도 검토 |

> 💡 관점 정리: 위 리스크는 "아이디어의 결격 사유"가 아니라 모든 양면 플랫폼이 공유하는 초기 과제다. 리스크를 인지하고 대응 설계를 갖춘 것 자체가 심사 방어 논리가 된다.
