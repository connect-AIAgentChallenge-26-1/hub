# ShowUp 1주차 발표 — AI Agent Challenge (7/10 금요일)

## 발표 대본

### (1) 도입 — 문제 (1분)

안녕하세요. N167 채민석입니다.

ShowUp은 예약제로 운영하는 소상공인이 노쇼, 폭언, 환불 분쟁 같은 문제 고객을 반복해서 겪으면서도, 기록하고 예약 전에 확인할 수단이 없어 같은 피해를 계속 반복하는 문제를 해결하는 웹서비스입니다.

기존 예약 앱(네이버예약, 캐치테이블)은 예약 접수에 집중하고, 문제 고객 이력 관리나 사전 경고 기능이 없습니다. ShowUp은 이 빈자리를 채웁니다.

핵심은 **자동 차단이 아니라 참고 지표**입니다. 사장님이 최종 판단을 내리되, 위험도를 한눈에 보여주어 판단을 돕습니다.

---

### (2) 핵심 기능 (1분)

MVP 기능 2개를 확정했습니다.

**1. 고객 이벤트 기록**
- 예약 상태를 방문 / 노쇼 / 당일 취소 중 하나로 원터치 기록
- 매장에서 폭언이나 무리한 요구가 있으면 사건으로 기록 (카테고리 4종 + 사실 메모)

**2. 위험도 조회 + 자동 경고**
- 전화번호 뒤 4자리나 이름으로 검색
- 위험도 3등급 표시 (안심 / 주의 / 위험)
- 노쇼 3회 이상이거나 폭언 사건 1회 이상이면 경고 배너 강제 표시

---

### (3) 위험도 설계 (1.5분)

ShowUp의 차별점은 위험도 계산 로직입니다.

| 이벤트 | 점수 |
|--------|------|
| 노쇼 | +8 |
| 당일 취소 | +4 |
| 상습 지각 | +2 |
| 폭언·위협 | +10 |
| 환불 분쟁 | +6 |
| 무리한 요구 | +4 |
| **정상 방문** | **−1 (회복)** |

- 0–23 안심 / 24–39 주의 / 40+ 위험
- 폭언 1회 이상은 점수 무관 최소 주의 보장
- 최근 30일 내 노쇼 시 +5 가중

정상 방문 시 점수가 차감되어, 개선된 고객은 등급이 내려갑니다. 낙인이 아니라 참고 지표라는 설계 의도가 여기서 듭니다.

업계 관행은 2회 노쇼 시 경고, 3회 시 예약 제한입니다. ShowUp은 이보다 완화된 3회 기준에 제한 대신 경고만 하여, 사장님 재량을 보존하고 법적 리스크를 줄였습니다.

---

### (4) 기술 스택 (1분)

| 영역 | 선택 | 이유 |
|------|------|------|
| 프론트엔드 | React + Vite + TS + Tailwind | 빠른 개발, 타입 안정성 |
| 상태 | TanStack Query + Zustand | 서버/UI 상태 분리 |
| 폼 | React Hook Form + Zod | 검증 + 타입 연동 |
| 백엔드 | Firebase (Auth / Firestore / Hosting) | 가게 격리, 3주 내 배포 |

Firebase를 선택한 이유는 인증과 가게별 데이터 격리가 핵심인데 Firestore Security Rules가 정확히 부합하고, 3주 기간에 서버+DB+Auth를 직접 구축하는 건 범위 초과이기 때문입니다.

데이터 모델은 `stores → customers → reservations / incidents` 구조이고, 검색 비용을 줄이기 위해 `riskStats`를 비정규화 캐시로 고객 문서에 저장합니다.

### (6) AI 에이전트 활용 (1분)

작업은 Hermes Agent 프레임워크 + Ollama Pro 모델 4세션으로 분담했습니다. 모델별 강점에 맞춰 역할을 할당했습니다.

| 세션 | 모델 | 역할 |
|------|------|------|
| 리드 | GLM 5.2 | 기획·통합·일정 |
| 프론트엔드 | Qwen 3.5 | UI·컴포넌트 |
| 백엔드 | Kimi K2.7 Code | Firebase·데이터·로직 |
| 보안 | GPT-OSS 120B | Rules·마스킹·법무 |

핵심 포인트 두 가지:
- **인터페이스 우선**: 백엔드가 `schema.ts`를 먼저 확정하면 프론트엔드는 그 타입으로 mock 개발 — 세션 간 대기 최소화
- **문서 기반 가드레일**: 각 세션이 건드릴 수 있는 파일과 건드리면 안 되는 파일을 문서로 명시
