# 잔소리봇 AI 개발 워크플로우

## 1. 문서 목적

이 문서는 잔소리봇을 개발한 4주 동안의 계획, GitHub Issue, 코드 검토,
검증, 배포와 회고를 바탕으로 최종 AI 개발 워크플로우를 정리한다.

AI는 분석, 계획, 구현과 검토를 지원한다. 사람은 해결할 문제, 우선순위,
위험 수용 여부와 최종 완료 여부를 결정한다. AI가 작성한 코드나 완료 보고는
그 자체로 완료의 증거가 아니며, 실제 코드·테스트 결과·Preview 화면·실제 기기
결과를 다시 확인한 뒤 다음 단계로 이동한다.

이 문서는 저장소에 실제로 존재하는 Agent와 Skill, 테스트 도구와 배포 흐름만
다룬다. 별도의 Hook 자동화나 서버 스케줄러가 있다고 가정하지 않는다.

## 2. 핵심 원칙

1. **사람이 목적을 결정한다.** AI는 선택지를 제안하지만 무엇을 왜 만들지는
   사람이 결정한다.
2. **큰 작업은 검증 가능한 범위로 나눈다.** 한 Issue는 가능하면 하루 안에
   구현하고 완료 조건을 확인할 수 있는 크기로 만든다.
3. **계획을 승인한 뒤 구현한다.** 요구사항, 제외 범위, 데이터 계약과 위험을
   확인하기 전에는 코드를 바꾸지 않는다.
4. **구현 완료와 검증 완료를 구분한다.** 코드가 작성됐다는 사실만으로 기능을
   검증 완료로 표시하지 않는다.
5. **테스트 파일과 실행 결과를 구분한다.** 테스트가 존재하더라도 실제로 실행하지
   않았다면 통과했다고 보고하지 않는다.
6. **자동 테스트와 실환경 검증을 구분한다.** mock과 단위 테스트는 브라우저,
   PWA, Web Push와 실제 기기 동작을 대신하지 않는다.
7. **Preview와 Production을 구분한다.** Preview 결과는 Production 검증 결과가
   아니며, 환경변수와 배포된 commit도 각각 확인한다.
8. **증거가 부족하면 완료 처리하지 않는다.** 확인할 수 없는 항목은
   `BLOCKED` 또는 `NOT VERIFIED`로 남긴다.
9. **DB는 정상 경로로 다룬다.** 개발·Production DB에 테스트 데이터를 직접
   기록하지 않고, 격리된 테스트 DB가 확인되지 않으면 쓰기 검증을 중단한다.
10. **AI의 결과를 교차 검증한다.** 한 도구의 분석이나 완료 보고를 다른 도구와
    사람이 코드·라인·실행 결과 단위로 다시 확인한다.

## 3. 전체 워크플로우

```text
문제 정의
→ 저장소와 현재 상태 분석
→ Feature Slice 및 GitHub Issue 분해
→ 구현 계획 검토와 승인
→ Claude Code 또는 Codex를 활용한 구현
→ 자동 테스트와 빌드
→ Code Review
→ Feature Verify
→ work 브랜치 및 Vercel Preview 검증
→ 사람의 브라우저와 실제 기기 확인
→ main 병합 및 Vercel Production 배포
→ 남은 위험과 백로그 기록
```

현재 Git·배포 흐름은 다음과 같다.

```text
work → Vercel Preview → 검증 → main → Vercel Production
```

각 단계는 단순한 작업 순서가 아니라 다음 단계로 넘어가기 위한 검증 지점이다.
문제가 발견되면 무조건 앞으로 진행하지 않고, 원인이 시작된 단계로 돌아간다.

## 4. 단계별 입력·작업·검증·결과

| 단계 | 입력 | AI가 수행하는 일 | 사람이 결정·확인하는 일 | 검증 기준 | 결과물 | 문제 발생 시 |
| --- | --- | --- | --- | --- | --- | --- |
| 문제 정의 | 사용자 문제, 실제 사용 상황 | 문제와 요구사항을 구조화하고 모호한 부분을 찾음 | 해결할 문제, 우선순위, 제외 범위 결정 | 현재 제품 문제와 연결되는가 | 문제 정의와 목표 | 문제 정의로 돌아가 범위를 다시 정함 |
| 저장소 분석 | 요구사항, 현재 코드·문서·Git 상태 | 관련 호출 경로, 테스트, 데이터 계약과 기존 패턴 조사 | AI의 해석이 실제 코드와 맞는지 확인 | 추측이 아니라 파일과 코드 근거가 있는가 | 현재 구조와 영향 범위 | 관련 코드·문서 조사를 보강 |
| Feature Slice | 큰 요구사항, 조사 결과 | 하루 안에 구현·검증 가능한 Issue로 분해 | Issue 우선순위와 경계 승인 | 각 Issue에 사용자 가치와 완료 조건이 있는가 | Issue 계획과 순서 | 범위가 크면 다시 분할 |
| 구현 계획 | Issue, 제품 계약 | 예상 파일, 구현 순서, 테스트와 위험 제안 | API·DB 변경 허용 여부와 계획 승인 | 포함·제외 범위가 명확한가 | 승인된 구현 계획 | 요구사항 또는 Feature Slice 단계로 복귀 |
| 구현 | 승인된 계획, 기존 테스트 | Claude Code 또는 Codex가 최소 범위 코드·테스트 작성 지원 | 중간 판단, 제품 문구와 UX, 위험한 변경 확인 | 기존 계약과 패턴을 유지하는가 | 코드와 관련 테스트 | 실패 원인에 따라 계획 또는 구현 수정 |
| 자동 검증 | 구현 결과 | 관련 테스트, typecheck, lint, production build 실행 및 결과 정리 | 명령과 실제 결과가 보고와 일치하는지 확인 | 필요한 검증이 실제 실행됐는가 | 명령별 실행 결과 | 테스트 계약과 구현을 구분해 진단 |
| Code Review | diff, commit, PR 또는 지정 파일 | 기능 오류, 데이터 무결성, 경합, 에러 처리, 테스트·배포 위험 검토 | 발견한 위험을 수정할지 수용할지 판단 | 재현 가능한 결함과 코드 근거가 있는가 | severity가 포함된 리뷰 | 구현 단계로 돌아가 최소 수정 |
| Feature Verify | 완료 조건, 코드, 실행 증거 | 항목별 `PASS`, `FAIL`, `BLOCKED`, `NOT VERIFIED` 판정 | 미확인 항목을 추가 검증할지 결정 | 모든 필수 완료 조건에 증거가 있는가 | 완료 조건 검증표 | 누락된 구현·테스트·환경 단계로 복귀 |
| Preview 검증 | work 브랜치 배포 | 배포 commit, 환경 차이와 확인 항목 정리 | 실제 브라우저·반응형·핵심 흐름 확인 | 의도한 commit과 번들이 실행되는가 | Preview 검증 기록 | 코드, 환경변수, 배포 버전을 분리 진단 |
| 실제 기기 확인 | Preview 또는 Production | 재현 절차와 관찰 항목 정리 | PWA, Push, 모바일 UX를 실제 기기에서 확인 | mock이 아닌 실제 환경에서 동작하는가 | 브라우저·기기 확인 결과 | 권한, 구독, SW, 네트워크를 분리 진단 |
| Production 배포 | 검증된 work 변경 | 배포 전 체크 항목과 남은 위험 정리 | main 병합과 Production 반영 여부 최종 결정 | Preview와 다른 환경 조건도 확인했는가 | Production 배포 결과 | rollback 또는 수정 Issue로 분리 |
| 회고·백로그 | 배포 결과, 미확인 위험 | 시행착오, 문서 불일치와 후속 작업 구조화 | 수용할 위험과 다음 우선순위 결정 | 완료·백로그·미구현이 구분되는가 | checklist와 다음 Issue | 필요하면 문제 정의부터 새로 시작 |

## 5. Agent 역할

Agent는 특정 작업을 대신 끝내는 자동 실행기가 아니라, 분석과 판단의 품질을
높이는 읽기 중심 역할이다. 직접 branch, commit, push, merge를 완료하지 않으며
사람 대신 최종 승인하지 않는다.

### Feature Slice

큰 요구사항을 하루 안에 구현하고 검증할 수 있는 GitHub Issue 단위로 나눈다.

- 현재 구현·검증·백로그 상태 확인
- 사용자 가치가 있는 수직 범위 정의
- 작업 범위와 제외 범위 정리
- 구현 순서와 의존성 정리
- 관찰 가능한 완료 조건 작성
- 필요한 테스트와 실환경 검증 구분

### Code Review

코드 스타일 취향보다 실제 사용자와 데이터에 영향을 주는 결함을 우선한다.

- 기능 오류와 잘못된 상태 전환
- 데이터 무결성과 transaction 위험
- 비동기 응답 역전과 race condition(동시에 처리되어 결과가 뒤집히는 문제)
- API 입력·응답과 오류 계약
- 비밀정보와 배포 환경 위험
- 실제 실패 조건을 놓친 테스트
- 유지보수에 직접 영향을 주는 구조 문제

문제가 없으면 억지로 지적을 만들지 않는다. finding에는 파일 위치, 영향,
발생 조건, 근거, 최소 수정 방향과 필요한 검증을 기록한다.

### Feature Verify

구현자의 완료 보고가 아니라 완료 조건과 실행 증거를 기준으로 판단한다.

- `PASS`: 필수 조건과 필요한 검증이 모두 확인됨
- `FAIL`: 완료 조건을 만족하지 못한 근거가 있음
- `BLOCKED`: 환경·권한·DB 안전 문제로 필수 검증을 실행할 수 없음
- `NOT VERIFIED`: 필요한 검증을 수행하지 않았거나 증거가 부족함

실행한 테스트, 코드·API 근거, 브라우저 확인 환경, 미확인 사항과 남은 위험을
각각 구분해 기록한다.

## 6. Skill 역할

Skill은 Agent나 구현 도구가 작업할 때 따르는 프로젝트별 절차와 기준이다.
모든 작업에 모든 Skill을 기계적으로 적용하지 않고 필요한 Skill만 선택한다.

### Simple TDD

입력과 출력이 명확한 작은 로직에서 다음 순서를 사용한다.

```text
제품 계약 확인
→ 실패 테스트 작성(Red)
→ 최소 구현(Green)
→ 동작을 유지한 리팩터링
→ 관련 회귀 테스트
```

주요 적용 대상:

- 날짜·시간과 KST 경계 계산
- validation과 상태 변환
- 점수·알림 간격 계산
- Gemini 응답 검증과 fallback 선택
- Focus session 유효성 검사
- 멱등성(idempotency, 같은 요청을 반복해도 결과가 중복되지 않는 성질) 보조 로직

화면 전체, DB transaction, PWA와 실제 Push 검증을 이 Skill 하나로 완료 처리하지
않는다.

### Test Writer

변경 위험과 실행 경계에 맞는 테스트 수준을 선택하고 작성한다.

| 대상 | 테스트 수준 |
| --- | --- |
| 순수 함수와 상태 변환 | Vitest |
| React 렌더링과 사용자 상호작용 | React Testing Library |
| Express API 입력·응답·DB 결과 | Supertest |
| Landing부터 History까지의 사용자 흐름 | Playwright |
| Service Worker 이벤트 로직 | Vitest 기반 Service Worker 테스트 |
| PWA와 Web Push 실제 동작 | 자동 테스트 + 실제 브라우저·기기 검증 |

Supertest와 Playwright처럼 데이터를 생성할 수 있는 테스트는 격리된 테스트 DB가
확인된 경우에만 실행한다.

### Nagging Bot Design

잔소리봇과 Shared Journey의 실제 디자인 언어를 유지하며 UI를 검토한다.

- 기존 캐릭터와 날씨 에셋 사용
- Lv0~Lv4 색상과 감정 강도 일관성
- 차분하고 따뜻한 AI 동행자 경험
- Landing, Register, Home, Nudge, Focus, Completion, History의 연결감
- 데스크톱·태블릿·모바일 반응형
- 키보드, 대체 텍스트, 색상 대비와 reduced motion 접근성

새 캐릭터나 과도한 시각 효과보다 실제 제품의 토큰과 에셋을 우선한다.

## 7. AI 도구별 역할

| 도구 | 실제 역할 |
| --- | --- |
| Claude Code | 초기 기능 구현, Agent·Skill 활용, 테스트 작성과 반복 수정 |
| OpenAI Codex | 저장소 분석, 구현 계획 검토, 기능 구현 보조, UI/UX 개선, 독립적인 코드 리뷰 |
| Gemini | 개발 Agent가 아니라 서비스 내부에서 사용자의 할 일과 상황에 맞는 첫 행동을 생성하는 모델 |
| Rule-based fallback | Gemini 호출이나 응답 검증이 실패해도 사용자 흐름을 이어 주는 규칙 기반 대체 행동 |

Claude Code와 Codex는 경쟁 관계로 고정 분담하지 않았다. 작업 상황에 따라 둘 다
분석과 구현을 지원했으며, 한 도구의 결과를 다른 도구와 사람이 교차 검증했다.
Gemini는 개발 워크플로우를 운영하는 Agent가 아니라 제품 기능의 일부다.

## 8. 사람의 필수 판단 지점

다음 결정은 AI에게 위임하지 않는다.

1. 어떤 사용자 문제를 먼저 해결할지
2. 요구사항과 제외 범위가 적절한지
3. DB schema와 API 계약을 변경해도 되는지
4. AI가 보고한 테스트 결과가 실제 명령과 결과에 일치하는지
5. UI가 실제 브라우저와 모바일에서 자연스러운지
6. Preview 결과를 Production에 반영해도 되는지
7. 남은 위험을 현재 MVP에서 수용할 수 있는지
8. 기능을 완료, 검증 완료, 백로그 또는 미구현으로 분류할지

특히 DB 변경, 배포, 실제 사용자 데이터에 영향을 줄 수 있는 작업과 최종 완료
판정에는 사람의 명시적인 확인이 필요하다.

## 9. 검증 기준

### 반드시 구분할 상태

| 혼동하기 쉬운 표현 | 실제 구분 |
| --- | --- |
| 구현 완료 = 검증 완료 | 코드 작성과 완료 조건 검증은 별개다. |
| 테스트 파일 존재 = 테스트 실행 완료 | 실제 명령과 exit code가 있어야 실행 결과다. |
| 단위 테스트 통과 = 브라우저 동작 확인 | DOM, 권한, Service Worker와 기기 동작은 별도다. |
| Preview 검증 = Production 검증 | origin, 환경변수, commit과 번들이 다를 수 있다. |
| 알림 권한 허용 = Push 구독 존재 | `Notification.permission`과 `PushSubscription`은 별도 상태다. |
| AI 완료 보고 = 사람의 최종 승인 | 완료 보고는 검증해야 할 입력이다. |

### 변경 유형별 최소 검토

- 순수 함수: 관련 Vitest와 정책 경계값
- React UI: React Testing Library, 접근성, 필요한 viewport
- Express API: 입력 타입, 응답 계약, Supertest와 DB 결과
- 핵심 사용자 흐름: Playwright와 필요 시 수동 브라우저 확인
- PWA·Web Push: Service Worker 테스트와 실제 브라우저 또는 기기
- 배포: commit SHA, 환경변수, 실제 bundle과 Production 재확인

자동화된 Playwright 범위는 Landing, Register, Home, Focus, Completion, History의
핵심 흐름과 등록 폼 빈 값 검증이다. 등록 폼 새로고침, Focus 세션 새로고침 복구,
API 실패 UI는 남은 E2E 백로그이므로 기존 E2E가 있다는 이유로 검증 완료 처리하지
않는다.

## 10. 실패 시 복구 흐름

### 테스트 실패

```text
제품 계약과 기대 결과 재확인
→ 테스트 설정 문제인지 구현 문제인지 구분
→ 가장 작은 원인 수정
→ 관련 테스트와 인접 회귀 테스트 재실행
```

테스트를 통과시키기 위해 제품 계약을 임의로 약화하거나 실패 테스트를 삭제하지
않는다.

### 브라우저 또는 배포 실패

```text
UI·상태
→ 환경변수
→ 네트워크·API
→ Service Worker·cache
→ 배포 commit과 실제 bundle
→ 브라우저·기기 재검증
```

Preview에서는 현재 배포가 어떤 commit SHA와 번들을 제공하는지 먼저 확인한다.
브라우저 권한, 앱 상태와 Push 구독을 하나의 상태로 추측하지 않는다.

### 증거 부족

- `PASS`로 처리하지 않는다.
- 안전 문제로 실행할 수 없으면 `BLOCKED`로 기록한다.
- 실행하지 않았거나 기준이 불충분하면 `NOT VERIFIED`로 기록한다.
- 무엇이 부족한지, 왜 확인하지 못했는지, 어떤 환경과 담당 확인이 필요한지 쓴다.

## 11. 실제 프로젝트 적용 사례

### Gemini fallback

Gemini가 정상적인 첫 행동을 반환하면 검증 후 사용한다. 호출 실패나 품질 검증
실패 시 `source: "rule_based"`인 규칙 기반 행동으로 전환하여 사용자 흐름이
중단되지 않게 했다. 설정 누락처럼 숨기면 안 되는 오류는 정상 fallback과 구분했다.

### Web Push 재구독 진단

`Notification.permission === "granted"`여도
`pushManager.getSubscription() === null`일 수 있음을 확인했다. Navbar에서 권한과
구독 상태를 분리하고, 구독이 없으면 다시 권한을 요청하지 않고 재구독할 수 있게
했다. 자동 테스트뿐 아니라 Desktop Chrome·Edge와 iPhone 홈 화면 PWA에서 실제
Push 수신을 확인했다. Android Chrome 실기기 검증은 별도 백로그다.

### Focus session 계약

직접 시작과 개입 후 시작을 `entryMode`와 `entryLevel`로 구분하고, 화면에 표시할
`journeyLevel`을 별도로 유지했다. `microTask`, `generationSource`,
`memoryEvidence`를 포함한 session 저장·복구와 완료·멈추기 후 정리 흐름을 코드와
테스트로 검토했다. 자동화되지 않은 Focus 새로고침 복구 E2E는 별도로 남겼다.

### 날짜 기반 streak

완료 횟수가 아니라 KST 기준 연속 완료일을 계산하도록 순수 함수로 분리했다.
현재 시각을 인자로 주입하고 UTC timestamp에 KST offset을 적용해 OS timezone에
의존하지 않도록 했다. 같은 날 중복 완료와 정렬되지 않은 입력도 테스트했다.

### 화면과 반응형 검증

Landing, Register, Home, Nudge Modal, Focus, Completion, History를 실제 에셋과
현재 디자인 토큰으로 정리했다. 주요 화면은 데스크톱, 태블릿, 모바일 viewport에서
텍스트 overflow, 버튼 겹침, 이미지 crop과 접근성을 확인했다.

### 환경별 배포 검증

`work → Preview → main → Production`을 구분했다. Preview의 demo 간격과
Production의 실제 간격을 환경별로 확인하고, Preview 결과를 Production 검증으로
대체하지 않았다.

### Playwright 핵심 흐름

Playwright로 Landing 스모크, 등록 폼의 빈 값 검증과
할 일 생성 → Home → Focus 완료 → History 핵심 흐름을 자동화했다. 자동화 범위
밖의 브라우저 기능은 수동 검증 또는 백로그로 명시했다.

## 12. 회고와 다음 개선 방향

### 유지할 시행착오와 원칙

**DB 직접 조작 제안 거절**

Task의 `status`만 직접 바꾸면 대응 `TaskEvent`가 없어 History와 event 기반 화면이
어긋날 수 있음을 확인했다. 이후 개발 DB도 정상 API 경로로만 다루고, 테스트는
격리된 DB가 확인된 경우에만 실행하는 원칙을 세웠다.

**중복 Issue 재검토**

새 `lib/nudge.ts`를 만드는 Issue가 계획됐지만, 기존 `nudgeMessages.js`와
`buildNudgeMessage()`에 이미 기능이 통합된 사실을 확인했다. 계획 문서보다 현재
코드를 먼저 확인하고 중복 작업을 닫았다.

**알림 간격 기준 재검토**

할 일 유형별 고정 간격은 사용자 근거가 부족하다고 판단했다. 마감 긴급도와 현재
레벨을 조합하는 방식으로 기준을 다시 세우고, 순수 계산 로직과 테스트로 분리했다.

**테스트 DB 가드 재검토**

통합 테스트가 개발용 환경파일을 읽으면 테스트 DB가 없어도 개발 DB에 연결될 수
있는 위험을 발견했다. 서버 테스트는 전용 환경과 가드를 강화했으며, Playwright의
완전한 fail-closed DB 가드는 여전히 보강할 운영 위험으로 남겼다.

**AI 완료 보고 교차 검증**

한 도구가 작성한 구현과 완료 보고를 다른 도구가 파일·라인·테스트·데이터 흐름
단위로 다시 확인했다. “테스트가 모두 통과했다”는 문장보다 어떤 명령을 어떤
환경에서 실행했는지를 증거로 사용했다.

### 다음 개선 방향

- 서버 scheduler·Cron과 `nextNudgeAt` 영속화
- Focus 중 서버 알림 일시중지

검증 완료 항목, 백로그와 미구현 아이디어를 구분해 기록한다.
