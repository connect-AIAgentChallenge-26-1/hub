# 나만의 개발 워크플로우

## 0. 아이디어 선정부터 지금까지 — 어려움 중심 회고

이 프로젝트(Unix/Git 명령어 사전 웹서비스)는 매 단계마다 계획대로 매끄럽게 진행되지 않았다. 계획을 제대로 선정하고 그대로 따라가기보다는, 이리저리 시도해보면서 진행한 경우가 많았다. 각 단계에서 실제로 부딪힌 어려움과, 뒤늦게 다시 확인해보고서야 알게 된 사실들을 그대로 남긴다.

**아이디어 선정 — 차별화 불안**
프로젝트 아이디어가 너무 좁거나, 이미 있는 것(man 페이지, Google 검색, tldr류 치트시트, ChatGPT에게 직접 물어보기)과 다를 게 없는 건 아닌지 반복해서 불안했다. 추상적으로 "괜찮다"는 확신이 들지 않았는데, 실제로 도움이 된 건 구체적인 경쟁 대상과 하나씩 직접 비교해보는 것이었다. 그 결과 이 프로젝트의 진짜 차별점은 "한국어냐 영어냐"가 아니라(tldr류도 이미 그건 해결한다), 이 부트캠프의 실습 시나리오에 맞춘 좁고 정확한 큐레이션이라는 결론에 도달했다. 이 "정말 가치가 있는 프로젝트인가"라는 의심은 이후로도 여러 번, 다른 옷을 입고 계속 돌아왔다(실용성, 학습지원 기능 부족, "결국 문서 확인 아닌가" 등) — 매번 막연한 불안을 구체적 비교로 확인하며 넘겼다.

**기획/설계 단계 — 여러 AI 툴을 병행했지만, 코딩 실행은 한 곳에 집중**
기획서(plan.md) 초안은 Gemini에서 시작해 Claude가 최종적으로 통합·정리했고, 기술스택 비교에도 Gemini를 썼다(Python/Flask/SQLite 제안은 프로젝트 여건에 안 맞아 기각). 디자인은 Google Stitch로 초안을 뽑고 Figma Make와도 비교하려 했으나(크레딧 소진으로 실제 시각적 비교는 못 하고 추론으로 대체) 최종적으로 Claude Code에서 design-check Skill로 규칙을 굳혔다.

ChatGPT와는 "사전 사이트 구조 설계"라는 제목으로 긴 대화(2026-07-21)를 나눴는데, 여기서 나온 아이디어들이 실제로 여러 갈래로 이어졌다. ChatGPT는 처음에 위키낱말사전식의 정교한 DB 스키마(words/definitions/examples/etymology/synonyms/antonyms 등)를 제안했지만 **이건 채택하지 않고**, 실제로는 훨씬 단순한 commands/categories/scenarios 구조로 갔다. 반면 "이대로 만들면 검색만 되는 CRUD 프로젝트가 되기 쉽다"는 지적에서 시작된 "상황 기반 검색"(예: "파일 삭제"를 검색하면 `rm`/`rmdir`/`find`를 추천) 제안은 실제로 3주차에 만든 **상황별 명령어 묶음(시나리오) 기능의 원형**이 됐고, "`cs-dict ls`처럼 셸에서 명령어 이름을 치면 브라우저가 해당 상세페이지를 여는" CLI 아이디어는 이후 문서에 남긴 **"kman" CLI 백로그 아이디어**(아직 미구현)의 원형이 됐다. 반대로 DevDocs식 3단 레이아웃(사이드바+본문+목차), "무엇을 하고 싶나요?"를 앞세우고 Unix/Git 카테고리 선택을 뒤로 미루는 첫화면 구조, 타이핑 중 자동완성, "학습 경로(Path)" 단계별 커리큘럼 같은 제안은 **받아들이지 않았다** — 지금도 홈 화면은 카테고리 선택이 먼저고, UI는 3단이 아니라 터미널 콘셉트의 단일 컬럼이다. 즉 ChatGPT의 제안을 그대로 다 받아쓴 게 아니라, 스키마/레이아웃처럼 이미 자리 잡은 정체성과 충돌하는 것은 걸러내고, 상황 기반 검색처럼 실제 문제를 짚어주는 것만 골라서 반영했다.

이렇게 기획·설계 단계에서는 여러 AI 툴을 실제로 병행했지만, **정작 코드를 작성하는 실행 단계는 Claude Code 하나에 집중했다** — 강사가 권장한 "여러 Agent를 병행해 개발 경험을 쌓으라"는 조언은 코딩 단계까지는 이어지지 않았다.

**1주차 — 디자인 산출물 자체 모순, 그리고 참고할 레퍼런스 부재**
Google Stitch로 뽑은 두 산출물(`DESIGN.md`, `stitch.md`)이 서로 값이 달랐을 뿐 아니라, `DESIGN.md`는 자기 안에서도 모순이었다(YAML 색상 토큰과 본문 설명이 서로 다른 팔레트를 가리킴). 이걸 stitch.md 쪽 값으로 통일해서 해결한 뒤, 이후 디자인을 한 번 더 다듬어보려 시도했지만 이 프로젝트에 맞는 참고 레퍼런스를 찾지 못해 결국 처음 결정한 초안 그대로 유지하기로 하고 마무리했다.

**2주차 — Meilisearch 연동 중 실제 버그 3개**
검색 기능(Meilisearch)을 Express에 연동하는 과정에서 실제로 동작하지 않는 버그를 세 번 만났고, 그때마다 원인을 직접 추적해서 고쳐야 했다(패키지 실제 export 이름이 짐작과 달랐던 것, curl로 보낸 URL이 `&` 때문에 셸에서 잘린 것, `.env` 변수명 오타). 계획대로 매끄럽게 붙는 대신, 붙여보고 안 되면 원인을 파는 과정의 반복이었다.

**3주차 — 이해 없이 진행, 그리고 요일별 계획이 실제로는 지켜지지 않음**
categories DB 마이그레이션, 상황별 명령어 묶음(시나리오) 기능 등은 웹 개발 지식 없이 시간만 맞추려고, 이해를 다 못한 채 검증 없이 진행한 부분이 있다. 정직하게 남긴다 — 이 부분을 감추거나 성과로 포장하지 않는다.

나중에 다시 확인해보니, 3주차 미션은 원래 월~금 요일별로 나눠서 진행하게 되어 있었지만 실제로는 대부분 금요일 하루(Supabase 연동, 시나리오 기능, 아키텍처 다이어그램)에 몰려서 처리됐다. 예외적으로 목요일 미션이었던 TDD(테스트 먼저 작성 → 실패 확인 → 통과시키기)는 그 다음 주로 넘어가서야 실제로 케이스 표 작성 → Red 확인 → Green 확인 → 리팩토링까지 전 과정을 제대로 거쳐 완료됐다 — 다만 여전히 프론트엔드 한 함수(`isMeaningfulQuery.js`)에 국한됐고, 백엔드(Express 서버) 쪽 테스트 커버리지는 지금도 0이다. 그리고 금요일 미션이었던 "3주간의 워크플로우 정리(문서 초안+짧은 발표자료)"는 그 주에 전혀 이뤄지지 않고 통째로 빠졌다 — 지금 이 문서가 사실상 그 몫까지 함께 채우고 있다.

**4주차 — 우연히 발견한 배포 버그, 그리고 멘토 리뷰**
화요일 미션(FE/BE 배포)의 설정 자체는 그 전날 대부분 끝나 있었고, 실제 라이브 주소가 살아있는지 확인하다가 쇼케이스용 스크린샷을 찍는 과정에서 Agent가 `/unix` 페이지 등 `/`가 아닌 경로로 직접 접속하거나 새로고침하면 Vercel이 404를 반환하는 버그를 우연히 발견했다. React Router를 쓰는 SPA인데 `vercel.json`에 라우팅 폴백 설정이 없어서 생긴 문제였고, 모든 경로를 `index.html`로 보내는 rewrite 규칙 하나로 해결됐다. 사용자가 먼저 신고한 버그가 아니라 다른 작업(스크린샷) 중에 우연히 걸렸다는 점에서, "배포 후 대표 경로 하나만이 아니라 깊은 경로도 직접 확인해본다"는 절차가 그동안 없었다는 것도 함께 드러났다.

4주 동안 처음으로 외부 코드 리뷰(멘토 리뷰)를 받았다 — 그 전까지는 코드 리뷰 습관 자체가 없었다. 리뷰에서 나온 지적들 중 지금 반영할 수 있는 것과 이후로 미룰 것을 판단해야 했고, 동시에 전체 일정이 밀리는 상황(스케줄 슬립)도 함께 처리해야 했다.

**남아있는 구조적 사실 하나**: 이 서비스는 GET(조회) API만 있고 POST/PUT/DELETE는 하나도 없다. DB에 데이터를 넣은 유일한 방법은 개발자가 터미널에서 직접 돌린 일회성 마이그레이션 스크립트였다 — 사용자 조작으로 시작되는 실시간 쓰기(저장) 흐름은 한 번도 만들어진 적이 없다. 이는 서비스 성격상(조회 전용 사전, 로그인/기여 기능은 의도적으로 범위 밖) 자연스러운 결과이지만, 2주차 "수직슬라이스 완성" 기준이 "저장~조회를 눈으로 확인"이었다는 점에서 "저장"은 사실 사람이 손으로 스크립트를 돌린 것이었지, 화면에서 트리거되는 흐름은 아니었다는 것도 정직하게 남긴다.

**전체를 돌아보며**
"AI에게 다 맡긴 것 같다"는 불안은 4주 내내 반복된 게 아니라, 사실 프로젝트를 시작한 첫날 밤(주제 선정 전, 아이디어가 하나도 없어 부트캠프를 그만둘까 고민할 정도로 힘들었던 그 밤)부터 있었다. 그날도 AI가 낸 제안은 전부 거절하고, 스스로 에브리타임을 리서치하고, 새벽에 스스로 낸 아이디어들(학점관리/출석률관리/알바 계열)로 방향을 잡았다. 그런데도 "이건 내가 낸 아이디어가 아니었다"는 불안이 똑같이 올라왔고, 그때 "AI가 낸 아이디어는 전부 거절당했고 살아남은 건 다 본인이 낸 것"이라는 사실을 하나씩 짚어보고 나서야 가라앉았다. 즉 이 불안은 4주 동안 여러 번 새 옷을 입고 돌아왔지만, 매번 같은 방식 — 무엇을 실제로 선택했고 무엇을 거절했는지 구체적으로 되짚어보는 것 — 으로 풀렸다. 실제로는 독립적인 판단을 내린 순간들이 있었다 — 백엔드 서버를 직접 꺼보며 홈 화면과 검색 화면의 백엔드 의존성이 구조적으로 다르다는 걸 스스로 발견했고, 검색 순위 옵션 3가지 중 하나를 이유를 대며 직접 골랐고, 죽은 코드 정리 시 테스트 파일까지 함께 정리할지 트레이드오프를 스스로 따져 결정했고, Meilisearch 순위 규칙 변경의 실제 효과를 데이터를 직접 확인해가며 검증했다. ChatGPT와의 기획 대화에서도 제안을 전부 받아쓴 게 아니라 골라서 반영했다 — 상황 기반 검색(→ 시나리오 기능)은 채택하고, 정교한 word-sense DB 스키마와 DevDocs식 3단 레이아웃, 검색 우선 첫화면 구조는 프로젝트의 기존 정체성과 안 맞는다고 판단해 걸러냈다. 다만 이 모든 게 있었다고 해서 3주차의 "이해 없이 진행" 같은 부분이나, 작업을 작은 단위로 나누지 않고 몰아서 커밋한 습관, 여러 Agent를 코딩 단계까지 병행하지 못한 점이 없었던 일이 되는 건 아니다. 두 가지가 동시에 사실이다 — 어떤 부분에서는 진짜 판단이 있었고, 어떤 부분에서는 시간에 쫓겨 이해와 검증, 그리고 미션이 요구한 "방식"(작은 단위 개발, 그날그날의 기록, 여러 툴 병행) 없이 넘어갔다. 그리고 전체적으로 방향이 뚜렷했다기보다, 계획을 세우고 그대로 따라가기보다는 이리저리 시도해보며 진행한 경우가 많았다.

## 1~7. 반복된 작업 순서 (7단계)

각 단계: 입력 → 작업순서 → 확인기준 → 결과물

### 1. 계획
- **입력:** 그 주의 코스 미션 텍스트, 이전 주까지의 진행 상태(docs/plan.md, checklist.md, tasks.md)
- **작업순서:** 미션 요구사항 확인 → 이번 주/그날 끝낼 작업 단위로 쪼개기 → 우선순위 정하기(핵심 기능 먼저) → 필요 시 `.claude/skills/feature-slice`로 하위 이슈까지 분해
- **확인기준:** 하루 안에 끝낼 수 있는 크기인가, GitHub 이슈/Sub-issue로 등록됐는가
- **결과물:** `docs/tasks.md` 갱신, GitHub 이슈(4개 부모 + 17개 하위 이슈 사례)
- **솔직한 한계:** 계획대로 매일 나눠 진행되기보다, 여러 날 작업이 하루에 몰리는 경우가 잦았다(예: 3주차 대부분이 금요일 하루에 처리됨).

### 2. 구현
- **입력:** 계획 단계에서 정한 작업 단위(이슈)
- **작업순서:** mock 데이터로 화면 흐름 먼저 확인 → 실제 연결(BE/DB) → Agent와 함께 단계적으로 구현하되 단계마다 직접 검증·승인
- **확인기준:** 브라우저에서 실제로 동작 확인(Edge headless 스크린샷 또는 직접 `npm run dev`)
- **결과물:** 변경된 소스 코드(`src/`, `server/`)

### 3. 디자인 검증
- **입력:** 새로 만들거나 변경한 화면
- **작업순서:** `.claude/skills/design-check`로 `docs/design-system/DESIGN.md` 규칙(색상 변수, radius, 폰트 분리, 그리드 미사용 등) 대조
- **확인기준:** 위치→기대값→실제값→수정 형태로 어긋남이 없는가
- **결과물:** 수정된 CSS/컴포넌트, DESIGN.md 갱신(필요 시)

### 4. 기능 검증
- **입력:** 완성된 기능(수직 슬라이스 등)
- **작업순서:** `.claude/skills/feature-verify`로 요구사항대로 동작하는지 점검
- **확인기준:** 화면요청→서버처리→DB저장→응답→화면갱신까지 눈으로 직접 확인됐는가
- **결과물:** 검증 결과, 발견된 버그 목록

### 5. 테스트
- **입력:** 기능 검증에서 통과한 코드 중, 규칙이 분명한 함수(검증/계산/변환)

## 문제가 생겼을 때 재확인하는 순서

실제로 만났던 버그들을 기준으로 정리한 체크리스트:

1. **패키지 실제 export 이름 확인** — 문서/기억에 의존하지 말고 설치된 패키지를 직접 열어 확인 (예: `meilisearch` 패키지의 실제 export는 `Meilisearch`, 짐작했던 `MeiliSearch`가 아니었음)
2. **curl에 넘기는 URL의 특수문자 확인** — `&`가 있는데 따옴표로 안 감싸면 셸이 명령을 잘라서 백그라운드로 보냄
3. **환경변수 이름 오타 확인** — `.env`의 변수명이 코드에서 읽는 이름과 정확히 일치하는지
4. **한글 폰트가 실제로 로드되는지 확인** — `font-family`에 이름만 적혀 있다고 적용되는 게 아니라, `@import`/`<link>`로 실제로 불러오고 있는지, 그리고 각 폰트 스택(특히 mono 계열)에 한글 폴백이 있는지 (Gulim 대체 버그, 2라운드에 걸쳐 발생)
5. **줄바꿈(CRLF/LF) 확인** — Windows 에디터가 파일을 CRLF로 재저장하면 실제 내용 변경 없이도 git이 변경으로 잡음 → `.gitattributes`(`* text=auto eol=lf`) + `git add --renormalize .`로 해결
6. **가정 대신 데이터로 직접 검증** — "이 규칙이 실제로 효과가 있는가" 같은 질문은 추측하지 말고 실제 데이터를 조회해서 확인
7. **의존성 방향 직접 확인** — 서버를 꺼봐서 어느 화면이 백엔드에 의존하고 어느 화면은 독립적인지 실제로 테스트
8. **배포 후 대표 경로 하나만 보지 말고 깊은 경로도 확인** — `/`만 확인하고 끝내지 말고, `/commands/:id`처럼 직접 URL 진입이나 새로고침이 가능한 깊은 경로도 배포 환경에서 직접 열어볼 것 (Vercel SPA 라우팅 404를 스크린샷 찍다가 우연히 발견한 경험에서)
