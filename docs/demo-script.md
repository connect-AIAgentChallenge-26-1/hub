## 예상 Q&A (심사 대비)

발표 후 나올 법한 질문에 대한 답. 약점 변명이 아니라 **의도된 설계 판단**으로 말한다.

### Q. 왜 멀티 매장(여러 빨래방)을 지원하지 않았나?

**한 줄 답:** MVP에서 검증할 가설은 "**전력 센서만으로 방치 세탁물을 자동 감지·대응할 수 있는가**"였고, 그건 매장 1곳에서 증명하면 되는 문제다. 매장 수를 늘리는 건 가설이 참일 때 붙는 확장 문제라 의도적으로 뒤로 뒀다.

- **가장 위험한 곳에 자원을 몰았다.** 진짜 불확실했던 건 멀티 매장 인프라가 아니라 "실제 세탁기 전력 곡선으로 상태·방치를 정확히 판정할 수 있는가"였다. 그래서 실측(CSV 34분 전체 사이클)·임계값 확정·상태머신·실매장 검증에 시간을 썼다. 멀티 매장은 알려진 패턴(테이블에 매장 구분자, 계정 스코핑)이라 리스크가 낮아 나중에 해도 된다.
- **멀티 매장은 로그인 화면이 아니라 데이터 모델 재설계다.** `store` 테이블 + 모든 테이블에 매장 구분 + 매장별 인증. 검증 안 된 확장 기능에 스키마를 미리 묶으면 핵심(감지 정확도)을 다듬을 시간을 뺏긴다.
- **확장 경로는 이미 열려 있다 — 막다른 길이 아니다.** 데이터가 매장 단위로 자연스럽게 나뉘는 구조(기계→세션→알림)라 매장 구분자 하나 붙이면 확장된다. "지금 안 한 것"이지 "못 하는 것"이 아니다.

**되받아치면**
- "그럼 사업성 없는 거 아니냐?" → 반대다. 한 매장에서 사장님 부담이 실제로 준다는 걸 증명하는 게 다른 매장에 파는 근거다. 확장은 검증 **다음** 순서다.
- "확장할 때 다 갈아엎어야 하는 거 아니냐?" → 아니다. 매장 구분자를 더하는 방식이라 기존 로직은 그대로 재사용된다. 단일 매장으로 만든 것도 낭비가 아니다.

> 배포본은 매장 1곳·DB 1개·패스코드 1개다. 발표에서 "어느 빨래방이든 바로 쓸 수 있다"고 말하면 과장이 된다 — "이 매장에서 검증했고, 멀티 매장은 다음 단계"로 말한다.
