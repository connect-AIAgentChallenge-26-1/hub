최근 API 기반 제품 구조를 Codex 문서형 작업장으로 전환한 결과가 제품 기획서와

다시 정리한다.

논의를 거치며 목표를 다음까지 확장했다.

- `docs/plan.md`를 에이전트 제품 기획서로 복원한다.
- `docs/checklist.md`를 기능 개발 진행표로 재구성한다.
- 로컬 리소스·태스크·일정 현황 기능을 문서형 workflow로 정의한다.
- 게임 기획 문서를 타입별로 전문화한다.

## 주요 결정

### Plan과 Checklist의 역할

초기에는 checklist를 운영 중 반복 확인하는 점검표로 해석했다.

사용자 정정:

- `docs/plan.md`는 이 에이전트 자체의 제품 기획서다.
- `docs/checklist.md`는 에이전트 기능을 개발 단위로 나누고 진행 상태를 표시하는 문서다.
- 실제 게임 프로젝트 운영 상태를 checklist의 주된 내용으로 넣지 않는다.

결정:

- plan에는 목표 기능, 승인 경계, 데이터 흐름, 완료 기준을 기록한다.
- checklist에는 기능별 구현과 검증 상태를 기록한다.
- 이번 구현 범위가 완료되면 해당 개발 항목을 완료 처리한다.

### 현재 단계의 목표

빈 Project Brief를 보고 실제 게임 기획을 시작하는 흐름을 제안했지만 사용자가
현재 목적은 게임 제작이 아니라 에이전트 기능 개발이라고 정정했다.

결정:

- 실제 게임 정보 입력은 시작하지 않는다.
- Project Brief는 `TBD` 상태를 유지한다.
- 에이전트 기능과 규칙, template, workflow를 먼저 완성한다.

### 로컬 PM 기능 범위

일정 관리 기능은 AI가 일정을 생성하거나 재배정하는 기능이 아니다.

결정:

- 사용자가 입력한 태스크의 `complete`, `incomplete`, 마감일만 사용한다.
- 사용자가 완료 상태를 알려주면 task board에 직접 반영한다.
- AI는 완료율, 지연 태스크, D-Day, 남은 기간, 일정 미정 항목을 보고한다.
- AI가 상태, 마감일, 담당자를 추정하거나 자동 변경하지 않는다.
- 리마인더 발송, 일정 재배정, 담당자 평가는 제외한다.

### 승인 경계

- 확정 설계 문서와 AI가 추론한 리소스·태스크 후보는 승인 후 반영한다.
- 사용자가 직접 명시한 태스크 추가, 수정, 완료 상태는 별도 승인 없이 반영한다.
- 확정 설계 변경만 Version History에 기록한다.
- AI 리소스·태스크 후보 승인은 Decision Log에는 기록하지만 Version History에는 기록하지 않는다.
- 승인 항목은 대상별 원본 hash를 기록하고 적용 직전에 다시 비교한다.
- 신규 대상은 `not_created` 기준과 동일 제목·주제 부재를 다시 확인한다.

### 다음 기능 우선순위

다음 개발 후보로 회귀 검증, 문서별 기획 전문화, 승인 변경 정밀화를 비교했다.

사용자 선택:

- 문서별 기획 전문화를 우선한다.

결정:

- 범용 template 하나로 모든 문서를 처리하지 않는다.
- 자주 쓰는 문서 타입은 필드와 검토 기준을 전문화한다.
- 장르 고유 문서는 범용 fallback을 유지한다.

### 전문 문서 타입

기존 6종만으로는 모든 장르를 감당하기 어렵다고 판단했다.

결정한 전문 타입:

- `system`
- `world_setting`
- `narrative`
- `character`
- `quest`
- `item`
- `level`
- `balance_economy`
- `ui`

별칭:

- NPC -> character
- 시나리오·스토리 -> narrative
- 맵·스테이지·던전 -> level
- 밸런스·경제·재화 -> balance_economy

resource, meeting_note, task는 기존 전용 workflow를 사용한다.

### 프로젝트별 Document Plan

Document Plan은 기획서 본문을 저장하는 문서가 아니다.

결정:

- 저장소 하나가 게임 프로젝트 하나를 담당한다.
- 게임을 추가하면 새 저장소 또는 workspace에 해당 게임의 Document Plan을 둔다.
- Document Plan에는 타입, 필요도, 사용자 결정, 상태, 이유, 관련 경로만 기록한다.
- 실제 원본, 미승인 전문, 확정 전문은 각각 Materials, Approval Queue,
  Confirmed Design에 저장한다.
- 장르, 핵심 플레이 경험, 주요 콘텐츠 특징을 모두 확인한 뒤 문서 구성을 추천한다.
- 지원 template 이름과 용도를 사용자에게 먼저 알린다.
- 타입별로 required, recommended, excluded를 제안한다.
- 9종 전체를 강제하지 않고 프로젝트에 필요한 일부만 선택할 수 있다.
- 세계관이나 서사가 없는 게임에는 관련 문서를 만들거나 질문하지 않는다.
- Document Plan은 가이드이며 계획 밖 문서를 차단하지 않는다.

재검토 조건:

- 장르 변경
- 핵심 플레이 루프 변경
- 스토리, 스테이지, 성장, 경제 구조의 큰 변경
- 플랫폼 또는 입력 방식의 큰 변경

### 문서 타입 판정

- 요청과 기존 자료로 타입이 하나면 에이전트가 자동 선택한다.
- 선택한 template 이름과 용도를 사용자에게 알린다.
- 둘 이상의 타입이 가능하면 후보와 이유를 제시하고 질문한다.
- 9종에 자연스럽게 들어가지 않으면 범용 fallback을 사용하고 이유를 기록한다.

### 문서 저장 Gate

초기에는 모든 필드를 채운 뒤 저장하는 엄격한 방식을 검토했다. 논의 결과
미정 정보를 허용하되 빈 골격은 저장하지 않는 방식으로 정했다.

결정:

1. 첫 입력에서 template 필드를 매핑한다.
2. unanswered 필드가 있으면 파일을 만들지 않고 한 번에 질문한다.
3. 사용자는 실제 값, `TBD`, `N/A + 사유` 중 하나로 답한다.
4. 후속 답변 뒤 모든 필드를 다시 검사한다.
5. administrative metadata, 제목, source 경로를 제외한 실제 기획 정보가 하나 이상 있어야 한다.
6. 모든 정보가 `TBD`·`N/A`이면 저장하지 않는다.
7. unanswered 또는 사유 없는 `N/A`가 남아도 저장하지 않는다.
8. gate를 통과하면 별도 incomplete draft 없이 Approval Queue에 자동 저장한다.
9. 사용자 승인 전에는 `workspace/design/`을 수정하지 않는다.

### 원본 자료 기반 기획서 작성

사용자는 기획서를 먼저 만들지 않고 세계관, 시나리오, 메모 등을 입력한 뒤
나중에 그 자료로 기획서를 만들 수 있기를 요청했다.

결정:

- Project Brief나 Document Plan이 없어도 원본 자료부터 등록할 수 있다.
- 입력 형식은 대화, Markdown, TXT를 지원한다.
- PDF와 DOCX는 Markdown 또는 TXT로 변환한 뒤 등록한다.
- 대화 입력과 파일 복사본은 `workspace/materials/inbox/`에 둔다.
- source index에 ID, 경로, hash, authority, 후보 문서, 처리 상태를 기록한다.
- authority는 기본 reference이며 사용자가 지정하면 authoritative로 바꾼다.
- authoritative도 승인 없이 확정 사실이 되거나 기존 설계를 덮어쓰지 않는다.
- 자료 등록만으로 기획서를 자동 작성하지 않는다.
- 사용자가 명시적으로 요청할 때만 후보와 충돌을 분석한다.

자료 기반 작성 순서:

1. source hash와 index 상태를 확인한다.
2. Document Plan, 확정 설계, 승인 대기 항목, 관련 원본을 검색한다.
3. 기존 문서와 충돌하는지 확인한다.
4. 관련 문서가 없으면 create, 같은 주제가 있으면 update 후보로 둔다.
5. 하나의 원본에서 여러 전문 문서가 가능하면 후보를 보여준다.
6. 사용자가 선택한 문서를 별도 승인 항목으로 작성한다.
7. 선택하지 않은 후보는 unselected, 명시적으로 제외한 후보는 skipped로 둔다.
8. 대상과 source hash를 승인 적용 직전에 다시 확인한다.

### 원본 자동 삭제

사용자는 관련 기획서가 확정되면 원본 자료를 자동 삭제하는 방식을 선택했다.

안전 조건:

- pending, needs_revision, needs_reconfirmation, unselected 후보가 있으면 삭제하지 않는다.
- 모든 후보가 confirmed 또는 skipped일 때만 소비 완료로 본다.
- source index tombstone과 Decision Log의 핵심 사용 사실을 먼저 기록한다.
- `workspace/materials/inbox/`의 등록 복사본만 마지막 단계에서 삭제한다.
- 저장소 밖 원본, source index, Decision Log, Version History는 삭제하지 않는다.
- 삭제 실패 시 `delete_failed`로 남기고 적용된 확정 문서는 되돌리지 않는다.

한계:

- 자동 삭제 후 원본 전문은 복구할 수 없다.
- source ID, hash, 관련 확정 문서, 결정, 삭제일, 사용 사실 요약만 남는다.

대표 요청 시나리오를 검증했다. 실제 게임 데이터 품질 검증은 아직 수행하지 않았다.

## 현재 상태

- Codex 문서형 에이전트의 현재 계획 범위는 workflow, skill, template에 연결됐다.
- 개발 체크리스트는 현재 구현 범위 기준으로 완료 상태다.
- 실제 게임 Project Brief, Document Plan 추천 결과, 원본 자료, 확정 설계는 비어 있다.
- 현재 변경은 아직 커밋하지 않은 작업 트리에 남아 있다.

- 현재 규칙과 제품 방향은 `AGENTS.md`, README, `docs/plan.md`, Architecture,
