# [N030_김병조] - 포토 내비게이션 지도·DB·후보 등록 흐름 구현

## 주요 작업 리스트

- 네이버 지도 기반 포토스팟 탐색, 검색 이동, 마커·바텀시트 선택 상태 동기화
- 공식·후보 포토스팟 공통 상세 → 프레임 선택 → 카메라 오버레이 → 촬영 결과 흐름 구현
- Supabase Storage·DB에 초기 포토스팟, 예시 사진, 오버레이, 레이아웃 가이드 데이터 연결
- 후보 포토스팟 제안 후 DB 등록 및 지도 목록 즉시 반영
- YOLO Pose + SAM2 기반 인물 레이아웃 추출, 구도 비교 모듈 및 데이터셋 구성
- `showcase.json`, DB·보안·배포 관련 문서 정리

## 내가 설명할 수 있는 부분

후보 제안 기능은 사진과 가이드 데이터를 `FormData`로 Express 서버에 전달하고, 서버가 Storage 업로드와 DB 등록을 처리하도록 구성했습니다. 프런트에는 `service_role` 키를 두지 않고, 등록 성공 시 응답받은 후보 스팟을 상태에 추가해 지도와 목록에 바로 보이도록 했습니다.

## 아직 이해 못 한 부분

Supabase Storage 업로드와 DB 등록은 서로 다른 작업이라 중간에 실패하면 일부 데이터만 남을 수 있습니다. 현재는 실패 시 업로드 파일을 정리하는 보완 처리를 했지만, 실제 서비스에서 트랜잭션과 재시도 정책을 어떻게 운영하는지 더 학습하고 싶습니다.

## 새로 알게 된 것

이번 작업을 통해 DB는 단순히 데이터를 넣는 곳이 아니라, 서비스 규칙을 강제하는 구조라는 점을 더 분명히 이해했습니다.

`photo_spots`와 `photo_guides`를 분리하고 FK로 연결해, 하나의 장소에 여러 촬영 프레임을 안전하게 연결했습니다. 장소를 먼저 만들지 않으면 가이드를 등록할 수 없고, 삭제 시 연결 데이터를 어떻게 처리할지도 DB 관계로 관리할 수 있습니다.

또한 상태값을 `official`, `candidate`, `draft`, `approved`처럼 분리해두면 프런트 화면의 조건문에만 의존하지 않고, API 조회 단계에서 공식 스팟과 승인된 가이드만 사용자에게 보여줄 수 있습니다. `background_guide_json`의 배경선 개수를 최대 5개로 제한하는 `CHECK` 제약도 적용하면서, 입력 검증을 API와 DB가 함께 맡아야 한다는 점을 배웠습니다.

마지막으로 좌표, 프레임 유형, 상태처럼 자주 조회·필터링하는 값은 일반 컬럼으로 두고, 인물 윤곽·포즈·배경선처럼 형태가 달라질 수 있는 분석 결과만 JSONB로 저장하는 이유를 이해했습니다. 관계와 검색이 필요한 데이터는 컬럼으로, 유연한 분석 결과는 JSONB로 나누는 방식입니다.
