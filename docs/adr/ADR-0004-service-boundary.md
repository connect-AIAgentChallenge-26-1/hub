# ADR-0004 완성형 MVP 경계와 조건 확인 후 추천 시작

## 맥락과 문제

자연어 요청을 즉시 비동기 추천 Job으로 만들면 LLM이 잘못 추출한 지역, 예산이나
제외 조건이 그대로 외부 검색 비용과 잘못된 결과로 이어진다. 반대로 모든 조건을
처음부터 구조화 form으로만 받으면 자연어 입력의 편의와 Agentic AI의 역할이 약해진다.
서비스 완료 범위도 백엔드 추천만으로 볼지, 공유·투표·최종 확정까지 볼지 고정해야
Task 완료를 일관되게 판단할 수 있다.

## 판단 기준과 검토 대안

기준은 사용자 통제, 잘못된 외부 호출 방지, 첫 사용의 간결함, 전체 결정 비용 감소와
검증 가능한 완료 경계다.

- 자연어 입력 즉시 Job 생성은 단계가 짧지만 추출 오류를 사용자가 바로잡지 못한다.
- 구조화 form만 사용하면 결정성은 높지만 자연어 조건 입력의 제품 가치가 줄어든다.
- AI 초안을 사용자에게 보여준 뒤 수정·확정하게 하면 한 단계가 늘지만 사용자 통제와
  외부 호출 안전성을 함께 확보한다.

## 결정

익명 세션에서 자연어 조건을 받아 동기적으로 추천 조건 draft를 생성한다. 사용자는
지역, 장소 유형, 인원, 1인 예산 범위, 선호·제외 조건과 우선순위를 수정하고 확정한다.
확정된 draft만 비동기 추천 Job으로 전환하며 Job 생성은 `202 Accepted`를 반환한다.

완성형 MVP는 추천 결과 3개를 근거와 함께 제공하고, 공유방에서 여러 익명 참여자가
LIKE/DISLIKE를 변경·삭제하며, 주최자가 한 장소를 최종 확정해 공유하는 흐름까지다.
실제 Naver와 Elice adapter, Mock 기반 CI, 보안·관측·부하 검증과 Java 17 운영
패키징을 포함한다.

회원제, 관리자 UI, 결제, 지도·길찾기, 네이티브 앱과 유료 클라우드 배포는 제외한다.

## 결과와 트레이드오프

잘못 추출된 조건이 비용과 실패로 증폭되기 전에 사용자가 수정할 수 있고, draft와
Job의 책임이 분리된다. 대신 API와 UI 단계, draft 저장·소유권·30분 만료 관리가
추가된다. 서비스 완료는 단순 추천 성공이 아니라 공유 의사결정 종료까지 검증해야
하므로 E2E 범위가 커진다.

## 검증과 재검토 조건

두 브라우저 세션을 사용하는 E2E에서 조건 추출·수정·확정, 202 Job, 결과, 투표와
최종 확정이 연결되어야 한다. 사용성 검증에서 draft 확인 단계의 이탈 비용이 오류
방지 효과보다 크다고 측정되거나, 인증 사용자용 저장 흐름이 제품 범위에 들어오면
단계와 보존 정책을 재검토한다.
