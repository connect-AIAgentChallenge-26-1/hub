# GameForge Agent — 5주차 작업 세분화 (Day 19~22)

> 원 기획서 11번 "Feature Expansion Workflow"를 구현한다. 지금까지 만든 9단계 워크플로우는 **새 프로젝트를 처음부터 만드는** 흐름이었다면, 이건 **이미 있는 프로젝트에 기능 하나를 추가**하는 흐름이다 — "대시 기능을 추가해줘" 한 마디로 시작해서 설계→ScriptableObject→코드→리뷰→문서화→커밋까지 이어진다.
>
> **좋은 소식**: 6단계 대부분을 처음부터 새로 만들 필요가 없다. 이미 있는 Agent와 파이프라인(7단계 코드 생성의 v9 기존코드 컨텍스트, 8단계 코드 리뷰, v4 원자적 커밋, v6 문법 검증)을 그대로 재사용한다. 이번 스프린트는 **"짧은 요청 한 줄로 시작하는 축소판 워크플로우"를 새로 조립하는 작업**에 가깝다.

**기획서 11번 원문 6단계 ↔ 재사용/신규 매핑**

| 기획서 단계 | 재사용 | 신규 필요 |
|---|---|---|
| 1. 설계 변경 제안 | System/Architecture Agent와 유사한 채팅 패턴 | 자유 텍스트 요청 → 설계 변경안 생성 흐름 |
| 2. ScriptableObject 생성 | 6단계(ScriptableObject 설계) Agent 로직 | 대상 프로젝트 범위 한정 |
| 3. Unity 코드 생성 | **7단계 Code Generation Agent 그대로 (v9 기존 코드 컨텍스트 포함)** | 거의 없음 |
| 4. 코드 리뷰 및 리팩토링 | **8단계 Code Review Agent 그대로 (v8, v6)** | 거의 없음 |
| 5. 변경 사항 문서화 | 9단계 Documentation Agent와 유사한 패턴 | 기능 단위로 범위 축소 |
| 6. Git Commit Message 생성 | **v4 원자적 커밋 파이프라인 그대로** | 거의 없음 |

## Day 19 — 진입점 + 데이터 모델

### 데이터 모델
- `data/users/{userId}/expansions/{expansion_id}/` 아래 새 네임스페이스 추가:
  - `request.json` — `{ description(사용자 원문 요청), status, created_at }`
  - `design.json` — 1단계 산출물(설계 변경안 Markdown, documents/{step_id}.json과 동일 스키마 재사용)
  - `scriptable-objects.json` — 2단계 산출물
  - `file-changes.json` — 3~4단계 산출물 (기존 file-changes 스키마 그대로 재사용: path, changeType, newContent, diff, syntaxValid 등)
  - `docs.json` — 5단계 산출물 (문서 스키마 재사용)
- 기존 9단계 `steps.json`과는 완전히 별개 — 프로젝트 생성 워크플로우가 끝난 뒤에도, 혹은 그와 무관하게 언제든 여러 번 실행 가능해야 함 (한 프로젝트에 기능 추가 요청이 여러 개 있을 수 있음 → `expansion_id`로 구분)

### 진입점 (프론트)
- Agent 워크스페이스 화면에 **"+ 기능 추가"** 버튼 신설 (사이드바 하단 또는 상단 액션 영역 — gameforge-ui-style 스킬 버튼 규칙 따름)
- 클릭 시 새 화면/모달: 자유 텍스트 입력창 하나 — "어떤 기능을 추가하고 싶으세요?" (예: "대시 기능을 추가해줘")
- 제출 시 `POST /api/expansions` — `expansion_id` 발급, `request.json` 저장, 1단계(설계 변경 제안) 화면으로 이동

**Day 19 완료 기준**: "+ 기능 추가" 버튼으로 자유 텍스트 요청을 입력하고 제출하면, 새로운 `expansion_id`가 발급되고 1단계 화면으로 이동한다.

## Day 20 — 1~2단계: 설계 변경 제안 + ScriptableObject 생성

### 1단계 — 설계 변경 제안 (채팅 기반)
- 사용자의 원문 요청 + **기존 프로젝트의 관련 설계 문서**(9단계 워크플로우로 만든 게 있다면 재사용, 없으면 최초 저장소 분석 결과)를 입력으로 Agent 호출
- 1~6단계 Agent와 동일한 채팅 UX 재사용: Agent가 "대시 이동 시 무적 프레임을 적용할까요?" 같은 질문을 하고, 사용자가 답하며 설계를 구체화
- 질문이 끝나면(또는 "지금까지 내용으로 문서 만들기" 버튼으로) 설계 변경안 Markdown 자동 생성 → 편집/승인 (기존 4.4/4.5 컴포넌트 재사용)

### 2단계 — ScriptableObject 생성
- 1단계에서 승인된 설계 변경안을 입력으로, 6단계 ScriptableObject 설계 Agent와 동일한 프롬프트 패턴으로 호출
- 이것도 채팅 없이 자동 생성 후 편집/승인 방식으로 갈지, 1단계처럼 채팅으로 갈지 결정 필요 — **디폴트는 자동 생성 후 수정만(9단계 패턴과 동일)**으로 진행하고, 필요하면 조정

**Day 20 완료 기준**: 기능 요청 제출 후 설계 변경안이 채팅으로 만들어지고 승인되면, ScriptableObject 설계 문서가 자동 생성되어 편집·승인까지 이어진다.

## Day 21 — 3~4단계: 코드 생성 + 코드 리뷰 (기존 파이프라인 재사용)

### 3단계 — Unity 코드 생성
- **7단계 Code Generation Agent를 그대로 호출** — 입력만 "1~6단계 전체 설계 문서"에서 "이번 기능의 설계 변경안(1단계) + ScriptableObject(2단계) + v9의 기존 코드 컨텍스트 탐색 로직"으로 축소
- v9의 클래스명 매칭 로직이 설계 변경안 문서에서도 똑같이 동작하는지 확인 (문서 형식이 다를 수 있으니 파싱 로직 재점검)
- 결과는 기존 커밋 리뷰 화면(FileChangeList, DiffViewer)으로 연결 — **화면 자체는 새로 안 만들고, expansion_id 기준으로 file-changes.json을 읽도록 데이터 소스만 분기**

### 4단계 — 코드 리뷰 및 리팩토링
- **8단계 Code Review Agent를 그대로 호출** — 입력은 3단계에서 만든 `newContent` (기존 8단계와 동일한 패턴)
- v6 문법 검증도 동일하게 적용

**Day 21 완료 기준**: 기능 요청의 설계·ScriptableObject 승인 후, 코드가 자동 생성되고 커밋 리뷰 화면에서 검토할 수 있다. 문법 오류가 있으면 기존과 동일하게 경고 표시된다.

## Day 22 — 5~6단계: 문서화 + 커밋 통합 + E2E 점검

### 5단계 — 변경 사항 문서화
- 9단계 Documentation Agent와 같은 패턴이되, **이번 기능 하나에 대한 변경 로그**로 범위를 좁힘 (전체 프로젝트 문서가 아니라 "이번에 무엇을 추가했는지" PR 설명 형태)
- 채팅 없이 자동 생성 → 편집만 (9단계와 동일)

### 6단계 — Git Commit Message 생성 + 실제 커밋
- **v4 원자적 커밋 파이프라인을 그대로 재사용** — 파일 단위로 커밋 메시지가 이미 3단계에서 생성되어 있으므로, 여기서는 최종 승인 후 실제 커밋만 트리거
- 5단계 문서도 함께 커밋 (예: `docs/changes/{expansion_id}.md` 같은 경로)

### 통합 점검
- "+ 기능 추가" 클릭 → 요청 입력 → 설계 채팅 → ScriptableObject → 코드 생성 → 코드 리뷰 → 문서화 → 실제 커밋까지 새로고침 없이 시연
- 같은 프로젝트에 대해 기능 추가 요청을 **두 번 연속** 실행해도 서로 독립적으로 동작하는지 확인 (`expansion_id`별로 데이터가 섞이지 않는지)
- `docs/GameForge_Agent.md`의 11번 항목 상태를 "스코프 밖" → "구현됨"으로 갱신, 8절/제외 목록에서도 제거

**Day 22 완료 기준 (= Feature Expansion Workflow 완성 체크리스트)**: 이미 존재하는 프로젝트에 "○○ 기능을 추가해줘"라고 요청하면, 설계 제안부터 실제 GitHub 커밋까지 전 과정이 사람 개입(승인/수정)과 함께 끝까지 진행된다.

## 이번 스프린트에서 하지 않는 것

- 기능 추가 요청 여러 개를 동시에 병렬 진행하는 것 (한 번에 하나씩만)
- 요청이 모호할 때 되묻는 정교한 처리 (일단 Agent가 최선으로 해석하고 진행, 이상하면 설계 단계 채팅에서 사람이 바로잡는 것으로 충분)
- 기존 9단계 워크플로우 자체를 아예 거치지 않은 "완전 외부" 저장소에 대한 기능 추가 (최초 분석은 여전히 필요)
