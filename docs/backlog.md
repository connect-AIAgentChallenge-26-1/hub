# CareerSignal 개발 백로그

이 문서는 CareerSignal의 개발 순서와 프로젝트 수준 이니셔티브를 관리한다. 실행 단위와 담당·일정·상태는 GitHub Issues와 GitHub Projects에서 관리하고, 배포 가능 여부는 [검증 체크리스트](checklist.md)에서 판정한다.

## 1. 관리 원칙

- 백로그 ID는 GitHub Issue 제목의 접두사로 사용한다.
- 하나의 백로그 항목은 하나 이상의 GitHub Issue로 분해할 수 있다.
- Phase의 순서는 시간이 아니라 의존 관계로 정한다.
- 세부 구현 단계, 일일 작업, 버그와 피드백은 GitHub Issue로 관리한다.
- 이 문서는 제품 범위, 순서, 완료 조건의 기준이다.
- 완료 상태는 연결된 Issue의 완료 조건과 검증 체크리스트를 모두 충족할 때 반영한다.

| 우선순위 | 기준 |
| --- | --- |
| P0 | 없으면 핵심 흐름이나 배포가 성립하지 않는 작업 |
| P1 | 베타 품질, 데이터 규모, 직무 확장과 발표 완성도를 높이는 작업 |
| P2 | 검증 뒤 도입하는 개인화·운영 확장 작업 |

### 1.1 일정 축

Phase 번호는 의존 관계를 나타내고 다음 일정은 프로젝트의 시간 순서를 나타낸다.

| 구간 | 계획 산출물 | 대응 범위 |
| --- | --- | --- |
| 1주차 | 문제 정의, 기획서, 화면 구조와 아키텍처 | `DOC-01`, Phase 0 |
| 2주차 | React·Express·DB·FastAPI 수직 슬라이스 | `FOUNDATION-01`~`FOUNDATION-04` |
| 3주차 | FastAPI 분석 경로와 에이전트 실행 계층 | Stage A~E |
| 4주차 | FastAPI 통합, 초기 자료 수집, 생성 데이터 서비스, 배포와 제출 자료 | Stage F, `DATA-02`, Phase 33 |
| 장기 | 실제 자료 확대, 직무별 실 데이터 활성화, 정기 수집·온디맨드 에이전트 전체 배포 | Phase 25~32 |

초기 수집은 Phase 5가, 장기적인 출처 발견과 갱신은 Phase 26·27이 맡는다. 생성 데이터를 먼저 적용한 결정은 최종 목표를 바꾸지 않고 두 단계의 순서만 분리한다.

착수한 Phase의 단위 표에만 상태 열을 둔다.

완료는 코드가 구현되고 `agent/tests/unit`·`agent/tests/eval`·`server/src/*.test.js`의 검사가 그 코드를 판정하는 상태다. 저장소에 남은 산출물이 어떤 데이터에서 나왔는가는 별개의 축이며, Phase 14에서 21까지가 만드는 저장 산출물은 전부 `dataset_version = ds_demo_v1`의 생성 데이터다. 실 데이터 실행 기록은 백엔드 직무 공고 44건의 파이프라인 확인뿐이다.

Phase 18과 20이 진행 중인 조건은 다음과 같다. Phase 18은 검사 5·6·7의 판정자 포트가 비어 있어 세 검사가 `not_applicable`로 기록되며, 판정자를 주입한 실행이 없다. Phase 20은 `docs/eval/`의 다섯 파일이 모두 `status = draft`이므로 게이트가 `not_gating`만 판정하고 활성화를 막거나 허용하는 판정에 이르지 않는다.

Phase 28이 진행 중인 조건은 직무 아홉 종의 카탈로그·화면 계약·분석 버전이 갖춰진 상태에서 전체 직무 화면이 생성 데이터 산출물을 사용한다는 것이다. Phase 33은 배포된 화면의 데모 시나리오와 발표 자료에 대한 사람 검증을 남긴다.

| 5-3 | 수집 에이전트 계약과 조사 요청 소비 인터페이스 | 완료 |
| 5-4 | 1차에서 3차 자료 적재와 출처 메타데이터 기록 | 완료 |
| 5-5 | 채용공고를 모집단으로 등록 | 완료 |

5-5는 매니페스트의 직무 판정과 대상군 표기로 `postings`와 `posting_versions`를 만든다. 모든 지표의 분모가 `posting_versions`이므로 이 단계 없이는 어떤 지표도 성립하지 않는다. 규칙은 [지표 명세](metric-spec.md) 2.1과 2.8에 있다.

5-4는 출처를 지정해 수집한다. 대상 선정과 이용 조건 확인이 선행하며 포털 크롤링을 쓰지 않는다. 접근 정책은 [데이터 전략](data-strategy.md) 8.1, 수집 대상 목록은 같은 문서 8.2에 있다. 출처 발견까지 수행하는 에이전트 실구현은 Phase 26이다. 두 경로 모두 5-3의 계약을 통해 같은 적재 파이프라인으로 들어온다.

적재 대상은 A에서 D까지 네 계층이다. 계층별 허용 용도는 [데이터 전략](data-strategy.md) 3장에 있다.

수집은 두 단계로 진행한다. 1단계는 목록과 출처 메타데이터를 매니페스트에 채워 기업군별 확보 가능 건수를 확인한다. 2단계는 원문을 받아 적재한다.

출처의 접근 방법은 직무와 무관하다. 직무를 확장할 때 `access_notes`와 `unreachable`을 직무별 파일에서 공용 파일로 분리한다. 분리 시점은 Phase 28이다.

표본 목표는 다음과 같다. 지표 정책 v1의 `minimum_n`은 5, `minimum_n_comparison`은 10이며 표본 판정은 범위와 대상군마다 따로 한다. 5-4의 목표는 건수가 아니라 어떤 지표가 성립하는가로 정한다.

| 순위 | 목표 | 조건 |
| --- | --- | --- |
| 1 | 신입·주니어 수치를 기간·대상군 비교에 사용한다 | `entry_junior` 분모 10 |
| 2 | 기업군 성향을 화면에 표시한다 | 기업군별 `experienced` 분모 5 |

기업군을 균등하게 채우는 것은 목표가 아니다. 기업군당 5건을 모아도 대상군으로 나뉘면 어느 칸도 `minimum_n`을 넘기지 못한다.

모든 기업군에서 모든 대상군의 최소 표본을 함께 채우는 규모는 MVP 범위 밖이다. 근거는 [지표 명세](metric-spec.md) 6장에 있다.

지표의 대상군 축은 5-4에 앞서 도입했다. 신입·주니어와 경력의 요구 수준을 같은 비교 기준에 섞지 않으며, 정의는 [지표 명세](metric-spec.md) 2.7에 있다.

### Phase 10. 승격과 버전 발행 — `TAX-01`

| 단위 | 완료 조건 | 상태 |
| --- | --- | --- |

심사 규칙은 순수 함수이며 저장소를 import 하지 않는다. 임계값은 `taxonomy_policy_version` 이 정하고 `tp_v1` 은 독립 공고 2건·독립 회사 2곳이다. 한 회사에서만 나타나는 표현은 승격하지 않는다. 판정별로 쓰는 자리가 다르다. 동의어는 별칭, 상하위와 관련은 차원과 관계, 해당 없음은 차원만 만든다.

심사 단위는 후보 하나가 아니라 라벨 묶음이다. 규칙과 근거는 [통계 모델](statistics-model.md) 3.4에 있다. 새 차원의 `dimension_kind` 는 후보가 담아 온 값을 옮기며, 값이 없으면 `practice` 로 떨어지되 그 횟수를 실행 결과에 남긴다.

버전 발행은 이전 활성 버전의 `superseded_at` 을 같은 거래에서 채워 부분 유니크 인덱스를 지킨다. 이어지는 차원과 별칭·관계는 새 버전으로 승계한다. 승계하지 않으면 새 버전의 기지 추출이 표기 변형을 놓친다. 생명주기 전이 규칙은 [통계 모델](statistics-model.md) 3.3에 있다.

### Phase 13. 지표 — `AGENT-02` `METRIC-01`

| 단위 | 완료 조건 | 상태 |

| 13-1 | 지표 family 실행과 적용 가능성 전개 | 완료 |
| 13-2 | 시간 연산자 | 완료 |
| 13-3 | 표본 상태 판정과 억제 | 완료 |
| 13-4 | 수치 검증 | 완료 |
| 13-5 | 역량별 깊이 프로파일 | 완료 |
| 13-6 | 표본 수렴 기록 | 완료 |

집계는 결정적으로 수행하며 생성 모델이 수치를 산출하지 않는다. 실행 조합은 `활성 지표 템플릿 × 적용 가능한 차원 또는 차원 쌍 × 범위 × 대상군 × 기간`으로 전개하고, 전개와 수식은 저장소를 import 하지 않는 순수 함수가 갖는다. 분자·분모의 정의는 [지표 명세](metric-spec.md) 3장, 전개 규칙은 같은 문서 5장에 있다. 차원이 하나도 없는 냉시작은 계산할 조합 없음으로 끝나며 어떤 집계 문장도 실행하지 않는다.

13-3은 별도 실행이 아니라 13-1과 13-2의 저장 경로에 붙는다. 표본 상태와 불확실성을 정하지 않고는 어떤 행도 저장할 수 없다. 최소 표본·억제 정책·불확실성 방법은 코드 상수가 아니라 `metric_policy_versions`의 행이며, 그 measure에 구간이 성립하는가는 정책이 아니라 수식이 정한다. 억제는 값만 비우고 행은 남긴다. 계산하지 못했다는 사실 자체가 화면의 정보이며, 행을 지우면 아직 안 돌린 것과 돌렸는데 표본이 없는 것을 구분할 수 없다.

13-2는 잇닿은 두 기간의 저장된 지표 행을 견준다. 델타 행은 나중 기간에 달리므로 기간을 건너뛴 쌍을 만들면 같은 유일 조건에 두 행이 생긴다. 두 기간 중 하나라도 비교 가능한 표본 상태가 아니면 행을 만들지 않고 사유를 남긴다. `temporal_delta` 전용 정책 행이 없으므로 기준 지표의 정책 버전을 그대로 쓴다.

13-4는 저장값을 만든 질의를 다시 실행하지 않는다. 걸러지지 않은 공고 버전 후보와 할당 원본을 받아 모집단 조건·중복 제거·활성 분류체계 조건을 파이썬에서 처음부터 다시 적용한다. 같은 질의를 두 번 실행하는 것은 대조가 아니다. 검사 목록은 [지표 명세](metric-spec.md) 7장에 있다.

13-5는 저장된 `depth_distribution`을 역량 단위로 합쳐 기대 깊이 하나를 고른다. 지표를 다시 세지 않는 이유는 다시 세면 그 사이에 적재가 늘었을 때 화면의 분포와 프로파일이 서로 다른 분모를 갖기 때문이다. 13-6은 데이터셋 충분성의 진단 자료이며 어떤 실행의 종료 사유도 아니다. 근거는 [통계 모델](statistics-model.md) 8장과 9장에 있다.

### Phase 13 통합 실행

`agent/scripts/stage_e.py`가 13-1에서 13-6까지를 실행한다. 실행 순서는 13-1 → 13-2 → 13-5 → 13-6 → 13-4이며 번호 순서가 아니다. 뒤 단계가 앞 단계의 저장된 행을 입력으로 쓴다. 단계마다 거래를 따로 열어 쓰기 주체가 다른 표를 한 거래에서 쓰지 않는다. 각 단계는 저장소 상태로 이어달리므로 별도의 체크포인트를 두지 않는다. 한 단계가 실행 전제의 실패로 끝나면 뒤 단계를 실행하지 않는다. Phase 13에는 생성 모델 호출이 없으므로 실행 전에 보여 주는 수는 예상 호출 수가 아니라 계산할 조합 수다. 산출물을 되돌리는 명령은 `agent/scripts/reset_stage_e.py`다.

### 생성 데이터와 실 데이터 교체

목표 직무 아홉 종의 화면이 조회하는 분석 산출물은 전부 `dataset_version = ds_demo_v1`을 갖고 분석 버전은 `an_demo_<job>`이다. 실 데이터는 같은 축의 다른 값으로 들어오므로 두 데이터가 한 표에서 섞이지 않는다. 결정과 제약은 [ADR 0015](adr/0015-generated-dataset-version.md), 식별자와 테이블별 규약은 [데모 시드 계약](../agent/data/demo_seed/CONTRACT.md)에 있다.

백엔드 직무의 실 공고 44건은 파이프라인 실행을 확인한 표본이다. 아홉 직무 화면의 수치는 생성 데이터에서 나오며 채용 시장의 사실이 아니다. 자료 확보와 서비스 완성의 순서를 분리한 근거는 [ADR 0017](adr/0017-generated-data-first.md)이 소유한다.

실 데이터로의 교체는 `DATA-05`(Phase 27)가 맡는다. 교체 단위는 직무 하나다. 한 직무의 실 공고가 Phase 8에서 20까지를 통과하면 그 직무의 새 분석 버전을 활성화하고, 나머지 직무는 생성 데이터의 활성 버전을 유지한다. 활성화가 직무 단위 원자 전환(21-1)이므로 아홉 직무를 한 번에 바꾸지 않아도 화면 계약이 성립한다. 되돌리기 조건은 `dataset_version = 'ds_demo_v1'`과 `analysis_version LIKE 'an_demo_%'`이며 범위는 ADR 0015에 있다.

`EXT-01`(Phase 28)은 Phase 27이 확보한 표본 위에서 직무별 매니페스트와 `access_notes`·`unreachable`의 공용 파일 분리를 수행한다.

## 13. GitHub Issue 운영 규칙

Issue 제목은 `[백로그 ID] 작업 요약` 형식을 사용한다.

```text
[TAX-01] 이중 경로 차원 추출 구현
[VER-01] 근거 함의 검사 구현
[METRIC-01] 지표 적용 가능성 전개 구현
```

각 Issue는 배경, 작업 범위와 제외 범위, 입력·출력 또는 변경 파일, 완료 조건, 검증 방법, 관련 백로그 ID와 선행 Issue를 포함한다.

GitHub Projects의 상태는 `Backlog`, `Ready`, `In progress`, `In review`, `Done`을 사용한다.
