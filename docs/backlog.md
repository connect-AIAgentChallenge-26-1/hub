## 백로그란

백로그(backlog)는 **아직 하지 않은 일을 우선순위 순으로 쌓아둔 목록**입니다. 원래 스크럼에서 나온 개념으로, 핵심은 "할 일 목록"이 아니라 **"순서가 있는 할 일 목록"**이라는 점입니다.

**왜 필요한가.** 4주는 하고 싶은 걸 다 하기엔 짧습니다. 백로그가 없으면 그때그때 눈에 띄는 걸 하게 되고, 마지막 주에 "정작 데모에 필요한 게 안 됐네"가 됩니다. 백로그의 진짜 역할은 할 일을 적는 게 아니라 **뭘 안 할지, 뭘 나중으로 미룰지를 미리 정해두는 것**입니다. 그래서 P0/P1/P2 우선순위가 목록 자체보다 중요합니다.

**어떻게 생겼나.** 한 줄이 하나의 Task이고, 각 줄에 최소한 이만큼이 붙습니다.

| 항목 | 뜻 |
|---|---|
| ID | 대화·커밋·PR에서 참조할 이름 (`T-08`) |
| Task | 큰 단위의 결과물. "무엇이 되면 끝인가"가 보이게 |
| 우선순위 | P0 / P1 / P2 |
| 담당 | 한 명. 둘이면 아무도 안 함 |
| 주차 | 언제 할지 |
| 의존 | 이게 끝나야 시작 가능한 선행 Task |
| 상태 | 대기 / 진행 / 완료 |

**어떻게 관리하나.** 세 가지만 지키면 됩니다.

1. **작업 시작 전에 상태를 `진행`으로 바꾼다.** 둘이 같은 걸 잡는 사고를 막습니다.
2. **주차가 끝나면 다시 정렬한다.** 백로그는 한 번 쓰고 마는 문서가 아니라, 매주 우선순위를 다시 매기는 살아있는 문서입니다. 안 끝난 P0는 다음 주 맨 위로, 못 한 P2는 미련 없이 버립니다.
3. **새 아이디어는 여기 맨 아래에만 적는다.** 코드에 바로 손대지 않습니다. 범위 확장(scope creep)은 이렇게 막습니다.

## 우선순위 기준

우선순위는 "중요해 보이는가"가 아니라 **"없으면 데모가 성립하는가"**로 정합니다.

| 등급 | 기준 | 못 하면 |
|---|---|---|
| **P0** | 없으면 핵심 흐름이 끊긴다 | 데모 자체가 불가능 |
| **P1** | 있어야 흐름이 완결된다 (분기 · 예외) | 데모는 되지만 반쪽 |
| **P2** | 있으면 좋다 | 버려도 무방 |

## 역할

| 담당 | 영역 |
|---|---|
| **서원** (`swlog`) | `client/` 화면 3개 · 디자인 시스템 적용 · 시뮬레이터 (백엔드 보조) |
| **도경** (`do-ttery`) | `server/` Express · SQLite · 상태 머신 · 알림 · Tapo 센서 연동 |

> **2026-07-20 결정**: 조회 API(T-13)는 예외적으로 서원이 맡는다. 도경의 3주차 백엔드 부담(T-10 상태 머신·T-11 방치 대응·T-12 Web Push)이 무거워 나눈 것. T-13은 DB를 읽기만 하는 조회 전용이라 상태 머신·알림 로직과 결합도가 낮고, 서원이 mock 응답 구조를 이미 설계해봐서 가장 자연스럽게 이어진다.

레이어(프론트/백엔드)로 나눴습니다. 화면별(고객/점주)로 나누지 않은 이유는 **두 화면이 같은 상태 머신과 같은 `session` 테이블을 보기 때문**입니다. 상태 머신은 어느 화면에도 속하지 않는 공통 심장이라 화면 기준으로는 잘리지 않습니다.

경계에서 만나는 지점은 **[CLAUDE.md](../CLAUDE.md)의 API Spec과 Data Model 하나뿐**입니다. 이미 확정돼 있으므로 서로를 기다릴 필요가 없습니다. 프론트는 그 구조 그대로 mock을 만들어 화면을 완성하고, 나중에 mock만 `fetch`로 갈아끼웁니다.

백엔드 쪽 짐이 훨씬 무거워서 **시뮬레이터(T-21)는 서원이 맡습니다.** 프론트가 화면을 실제 데이터로 돌려보려면 어차피 필요하고, 백엔드에서 가장 무거운 짐 하나를 덜어줍니다.

- ✅ 콘센트 방식 (직결 배선 아님)
- ✅ 매장 Wi-Fi 사용 가능

### ⚠️ 정격 입력 1.1kW가 의미하는 것 — T-05의 핵심

20kg 업소용인데 1.1kW라는 건 **전기 히터가 없다**는 뜻이다 (온수를 배관으로 받는 방식). 가정용 세탁기(히터 2~3kW)와 전력 곡선이 근본적으로 다르다.

**좋은 점** — 히터라는 큰 배경 부하가 없으니 모터 고속 회전이 유일한 대형 부하다. **탈수 스파이크가 매우 뚜렷하게 튄다.** RUNNING → SPIN 전이는 쉽게 잡힐 것이다.

**위험한 점** — 히터가 없으면 세탁 중 전력이 **모터 텀블(돌다-멈추다-돌다)만 따라간다.** 즉 **세탁 중에도 전력이 주기적으로 0W 근처까지 떨어진다.**

State Machine의 종료 판정은 이렇게 정의돼 있다.

> SPIN → DONE : 전력 0W 복귀 **유지**

**세탁 중 텀블 휴지기에 0W가 찍히면 종료로 오판한다.** "유지"가 몇 초인지가 전부다. 이 숫자를 놓치면 3주차 상태 머신이 세탁 중간에 "완료!" 알림을 보낸다.

**→ 실측 당일 반드시 잴 것: 세탁 중 텀블 휴지기가 최대 몇 초인가.**
종료 판정의 "유지" 시간은 그보다 넉넉히 길어야 한다. 이걸 안 재면 매장에 다시 가야 한다.

```
1주차  기획 · 프로토타입 · Agent 지침          ✅ 완료
2주차  뼈대 · 센서 실측 · ingest · 화면 3개(mock)   ✅ 완료
3주차  DB · 상태 머신 · 방치 대응 · Web Push · mock 제거   ← 지금
4주차  통합 테스트 · 실매장 검증 · 배포 · 데모
```

| 주차 | 서원 (프론트) | 도경 (백엔드) | 이 주가 끝나면 |
|---|---|---|---|
| **2** | T-01 T-02 T-14 T-15 T-16 T-21 | T-03 T-04 T-05 T-08 | 화면 3개가 mock으로 돌아가고, 실제 세탁기 전력 곡선이 찍힌다 |
| **3** | T-13 T-17 T-18 T-19 T-20 | T-06 T-07 T-09 T-10 T-11 T-12 | 시뮬레이터를 돌리면 방치가 자동 판정되고 알림이 온다 |
| **4** | T-24 (여유 있으면 T-27) | T-23 T-25 | 실제 매장에서 한 사이클이 돌고, 배포된 주소로 데모가 된다 |
| | T-22 T-26 (공동) | | |

**두 사람이 서로를 기다리는 지점은 한 곳입니다.**

- **T-05 → T-10**: 임계값이 나와야 상태 머신을 짤 수 있습니다. 2주차 안에 T-05가 안 끝나면 3주차 전체가 밀립니다. **가장 먼저 처리할 Task입니다.**

**같은 사람 안에서 순서가 있는 지점** (2026-07-20 T-13 담당 변경 이후)

- **T-13 → T-17**: 이제 둘 다 서원 담당이라 사람 간 대기가 아니라 순서 문제입니다. 조회 API(T-13)를 끝내야 mock 제거(T-17)를 시작할 수 있습니다.

## 2주차 완료 정의 (Definition of Done)

다음 주까지 아래 네 가지가 되면 2주차는 끝난 것으로 봅니다.

1. ✅ **`npm run dev` 한 번으로 `client`(5173)와 `server`(3000)가 같이 뜬다.** (T-01 완료)
2. **화면 3개(QR 랜딩 · 진행 · 대시보드)가 mock 데이터로 완성돼 있다.** 디자인 시스템(색·라운드·마스코트·문구 톤) 검증 체크리스트를 통과한다.
3. ✅ **실제 세탁기 1회의 전력 곡선이 CSV로 찍혀 있고, 상태별 W 임계값이 문서에 숫자로 적혀 있다.** (T-05 — 2026-07-20 2차 CSV 실측으로 확정)
4. ✅ **시뮬레이터를 돌리면 `POST /ingest/:machineId`가 데이터를 받는다.** (T-21 완료 — 정상 수거·방치·QR 미신청·센서 오류 4개 시나리오. 상태 판정은 T-10 이후)

2주차가 끝나면 이 문서를 다시 열어 우선순위를 재정렬합니다.

## 하지 않는 일

범위 확장을 막기 위해 **명시적으로 버립니다.** 좋은 아이디어라도 4주 안에는 하지 않습니다.

재고 관리 · 자동 발주 · 환불 처리 · 매출 분석 · 다중 매장 관리 · AI 운영 리포트 고도화 · 로그인/회원가입 · 결제 연동

승인 대기함은 **UI 자리만** 둡니다 (T-20). 기능은 만들지 않습니다.

## 아이디어 (다음에 볼 것)

새로 떠오른 건 코드에 손대지 말고 여기 적어둡니다. 매주 재정렬 때 P0~P2로 승격할지 판단합니다.

- **Tailwind 도입 검토** — 지금은 CSS Modules(`*.module.css`)를 씁니다. Vite 기본 지원이라 설정이 0이고, `OwnerDashboard`와 `LandingPage`가 둘 다 `.card`·`.bar`를 정의하고 있어 **클래스 격리가 실제로 일하고 있습니다.** Tailwind로 가면 `jsx` + `module.css` 짝이 사라지고 파일 수가 준다는 이점이 있지만, **이미 만든 화면 3개의 CSS를 전부 다시 써야 합니다** (반나절 이상). 4주 안에는 하지 않습니다. MVP를 끝낸 뒤 판단합니다.
- **네이티브 앱 전환 검토 (2026-07-22 제기, 07-22 구조 보완)** — T-18 실기기 테스트 중 iOS Web Push의 "홈 화면 추가 필수" 제약을 직접 겪고 나온 질문. iOS는 앱스토어 네이티브 앱만 제약 없이 푸시 알림을 받고, 웹사이트는 아무리 잘 만들어도 이 제약을 못 벗어난다(애플 정책, 우회 불가 — WebKit 강제로 크롬·삼성인터넷도 동일).
  - **구조안**: QR/웹은 지금처럼 설치 없는 기본 채널로 그대로 두고, 앱은 "확실한 알림을 원하는 손님"을 위한 선택적 상위 채널로 얹는 이중 구조. 매장 1곳뿐이라 QR 즉시 접속이라는 지금 장점을 앱으로 대체하지 않고 유지한다는 점에서 QR을 없애는 것보다 낫다.
  - **왜 지금은 아닌가**: 앱스토어 심사 소요 기간이 4주 로드맵과 안 맞고, 팀 스택(React 웹 + Express)과 네이티브/RN 개발이 별개 기술이라 처음부터 새로 배워야 함 — 범위 확장 금지 원칙과 충돌.
  - **더 가벼운 중간 단계로 Apple Wallet 패스(PassKit)** — 앱 설치 없이 "지갑에 추가"만으로 푸시성 업데이트 가능 — 도 검토 후보.
  - 지금은 결정하지 않음. MVP(4주) 종료 후 프로젝트를 계속 이어갈 경우에만 재검토.
- **멀티 매장(여러 빨래방) 지원 검토 (2026-07-29 제기)** — "다중 매장 관리"는 위 "하지 않는 일"에 이미 명시된 MVP 범위 밖 항목이다. 발표 준비 중 재차 논의됐고, **결론은 발표 후 도경님과 제대로 착수(지금 아님)**.
  - **왜 지금 아닌가**: MVP 가설("전력 센서만으로 방치 감지·대응")은 매장 1곳에서 검증하는 문제다. 멀티 매장은 가설이 참일 때 붙는 확장 문제. 발표 3일 전에 착수하면 잘 돌아가는 데모가 깨질 위험이 크다.
  - **왜 큰 작업인가 (로그인 화면 하나가 아님)**: ① `store` 테이블 추가 + `machine` 등에 매장 구분자(`store_id`) → **테이블 5개 고정 규칙(CLAUDE.md)을 깨는 결정** 필요. ② 사장님 구독(`session_id IS NULL`=이 매장)이 매장 여럿이면 구분 불가 → 매장별 인증으로 교체. ③ 조회 API·대시보드 전부 "이 매장만" 스코핑. ④ DB·서버·상태머신 = **도경님 영역**이라 단독 진행 불가.
  - **현재 대체물**: 배포 링크 공개 접근 차단은 단일 패스코드 잠금(`OWNER_PASSCODE`, `POST /api/owner/verify` + client `OwnerGate`)으로 처리 중 — 매장 1곳 전제 그대로, 멀티 매장 인증과는 별개다. 멀티 매장 착수 시 이 잠금은 매장별 진짜 인증으로 교체된다.
  - **확장은 막다른 길이 아니다**: 데이터가 매장 단위로 자연스럽게 나뉘는 구조라 매장 구분자 추가로 확장 가능. "지금 안 한 것"이지 "못 하는 것"이 아니다. 발표 Q&A 논리는 `docs/demo-script.md` "예상 Q&A" 참고.
