# 첫날 개발 하네스

**"첫날" 앱을 만드는 Claude 에이전트가 매번 같은 결과물을 내도록 스킬·에이전트·규칙을 한 세트로 묶은 개발 하네스.**

이 세트를 프로젝트 저장소에 두고 Claude Code(또는 다른 Claude 도구)에서 스킬을 설치·활성화하면, 화면·데이터·API·시각 가이드가 어느 세션에서 만들어져도 동일한 규격으로 조립됩니다.

---

## 1. 무엇이 들어 있나

```
cheotnal-harness/
├── README.md                              ← 이 문서
├── skills/
│   ├── cheotnal-design/                   ← 기존 SKILL.md (색·모양·어투)
│   ├── cheotnal-mock-data/                ← 데이터 스키마 (필드·타입·상태값)
│   ├── cheotnal-api-contract/             ← Express 엔드포인트·응답 봉투
│   └── cheotnal-visual-guide/             ← 시각 가이드 렌더링 구조
└── agents/
    ├── frontend-agent.md                  ← client/ 담당
    ├── backend-agent.md                   ← server/ 담당
    └── reviewer-agent.md                  ← 커밋 전 체크리스트 판정
```

---

## 2. 스킬은 각각 어떤 층을 결정하나

| 스킬 | 결정 층 | 없으면 흔들리는 것 |
|---|---|---|
| **design** | 색, 모서리, 말풍선 모양, 어투 | 세션마다 색조가 조금씩 달라짐 |
| **mock-data** | 각 엔티티의 필드명·타입·상태값 | 화면마다 `role`이 `sender`가 되고 `type`이 되고 오락가락 |
| **api-contract** | 엔드포인트 경로, 응답 봉투(`{data}`/`{error}`), 상태 코드 | 프론트가 가정한 응답 모양과 서버 응답이 안 맞음 |
| **visual-guide** | 이미지·마커·화살표·딤·CTA의 HTML/CSS 구조 | 시각 가이드 화면마다 구현 방식이 달라 유지보수 지옥 |

네 스킬은 서로 겹치지 않고 붙어 있어요. 예를 들어 시각 가이드는 데이터 스키마(mock-data)→ 렌더링(visual-guide)→ 색(design)→ API 응답(api-contract) 순으로 네 스킬이 다 관여합니다.

---

## 3. 에이전트 세 역할

Claude Code에서 서브에이전트를 쓰든, 단일 세션에서 역할을 바꿔가며 쓰든, 아래 역할과 담당 폴더는 지킵니다.

| 에이전트 | 만지는 폴더 | 절대 안 만지는 폴더 |
|---|---|---|
| 프론트엔드 | `client/` | `server/` |
| 백엔드 | `server/` | `client/` |
| 리뷰어 | (읽기만) 전체 | 코드 수정 자체가 금지 |

리뷰어는 커밋 직전에 스킬 체크리스트로 통과/실패 판정만 해요. 실패가 있으면 담당 에이전트에게 반려됩니다.

---

## 4. 설치·사용법

### Claude Code에서 쓸 때

1. `skills/` 아래 각 폴더를 `.claude/skills/`에 복사하거나, `.skill` 패키지를 임포트.
2. 프로젝트 루트에 이미 있는 `CLAUDE.md`가 프로젝트 규칙을, 스킬이 결과물 규격을 담당합니다.
3. 작업 시작 시 프롬프트에서 어느 에이전트 역할인지 명시:
   > "너는 프론트엔드 에이전트야. `agents/frontend-agent.md`를 읽고 시작해."
4. 큰 작업 뒤에는 리뷰어 역할로 세션을 한 번 굴려서 체크리스트를 통과시킵니다.

### Claude 웹/데스크톱에서 쓸 때

1. `.skill` 파일 카드에서 **Save skill** 버튼으로 프로필에 설치.
2. 대화 시작 시 이 README와 관련 에이전트 파일을 함께 첨부하면 됩니다.

## 6. 다음 단계에서 추가될 스킬 (아직 만들지 않음)

AI·DB·인증이 들어오는 단계에서 새 스킬 3개가 필요해요. 지금은 이름만 잡아둡니다.

| 스킬 (예정) | 담당 | 왜 필요한가 |
|---|---|---|
| **cheotnal-rag-pipeline** | 지침 저장 단위, 검색 방식, "지식 베이스에 없음" 폴백 흐름 | 기획서 4-2 돌발 상황 처리가 흔들리지 않게 |
| **cheotnal-persona-prompt** | 알바생·사장 어투별 시스템 프롬프트, 시나리오 질문 세트 | 어투가 화면 텍스트뿐 아니라 LLM 출력까지 일관되게 |
| **cheotnal-security** | API 키 관리, 익명성 보장 방법, rate limit, 사용자 입력 필터 | mock 단계엔 없던 보안 문제가 폭발적으로 늘어남 |

이 스킬들의 필요성이 실제로 커지면(=구현 코드가 나오기 시작하면) 그때 만드는 게 정확해요. 미리 만들면 상상만으로 규칙을 정하게 돼서 실제와 안 맞습니다.

## 7. 이 하네스가 지키는 4가지 목표

사용자가 원래 정한 기준을 그대로 반영했어요.

1. **기획서 상의 기능을 구현** — 네 스킬이 3대 핵심 기능(Q&A, 지침서, 불만 집계)의 결과물 규격을 세부 필드까지 고정.
2. **배포 가능한 퀄리티** — design 스킬의 색·간격 토큰, api-contract의 봉투·상태 코드가 통일된 완성도를 담보.
3. **유지보수 쉽게** — mock-data 스키마가 실 API 응답 모양과 같아서, `import mock` → `fetch('/api/...')` 한 줄 교체만으로 전환 가능.
4. **보안 문제 없음** — Complaint 익명성(mock-data), POST 본문 화이트리스트·에러 노출 금지(api-contract), 리뷰어의 자동 체크. 다음 단계 보안 스킬로 확장 여지.

각 목표를 지키는 게 어느 스킬의 몇 번 항목인지 커밋마다 리뷰어가 근거를 붙여줍니다.
