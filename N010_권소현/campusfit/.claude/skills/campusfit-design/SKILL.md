# 캠퍼스핏 디자인 skill

캠퍼스핏은 "카테고리마다 사이트가 갈라져 있고, 어디도 내가 대상인지 걸러주지 않는다"는 문제를
푸는 서비스다. 화면을 만들거나 검수할 때 [기획서.md](../../../기획서.md) + 이 문서 기준으로 판단한다.

**현재 디자인 기준본이 두 개다.** `design/prototype.html`은 라디오버튼 트릭으로 만든 정적 버전
(온보딩 2단계가 있는 구버전)이고, 실제 기준은 Claude Design에서 만든 최신본(로컬
`CampusFit Website (standalone).html`, 소스는 `CampusFit Website.dc.html`)이다 — **온보딩이
없고 필터가 옵션**이라는 게 가장 큰 차이다. 새 화면을 만들 땐 최신본의 흐름을 기준으로 삼고,
`prototype.html`은 아직 안 맞춰져 있다는 걸 감안한다. React 구현은 `client/src`에서 진행한다.

## 항상 먼저 할 것

새 화면을 만들기 전에 [design-tokens.css](../../../design/design-tokens.css)와
[design-system.md](../../../design/design-system.md)를 읽는다. 색·타이포·컴포넌트는
거기 있는 토큰만 쓰고, 새 색이나 새 radius 값을 임의로 추가하지 않는다.

## 톤 체크리스트 (디자인 결과가 의도와 맞는지 확인할 때)

- [ ] **필터링된 느낌이 나는가** — "검색"이나 "전체 목록에서 찾기"처럼 보이면 안 된다.
      단, 필터링은 카테고리(장학금/공모전/...) 자체를 숨기는 게 아니라 그 안의 공고
      목록에 적용되는 것이다. 온보딩에 관심분야 선택을 넣어 카테고리 자체를 다시
      고르게 했던 게 이 원칙 위반이었다 — 카테고리 내비게이션과 조건 필터링을
      섞지 않는다.
- [ ] **필터를 강제하지 않는가** — 국립/사립·지역·학년 조건은 온보딩처럼 막고 서있으면
      안 되고, 상단 "필터 설정" 버튼으로 원할 때 여는 옵션이어야 한다. 조건을
      안 정해도 홈 화면에서 바로 둘러볼 수 있어야 한다 (온보딩 자체를 없앤 이후 규칙).
- [ ] **학년 필터가 해당 카테고리에서만 작동하는가** — 학년은 장학금·인턴십처럼 공고에
      학년 조건이 실제로 있을 때만 걸러야 한다. 학년이 무관한 공고(지자체 혜택 등)에
      학년 필터를 강제로 적용해 결과가 사라지면 안 된다.
- [ ] **홈 화면이 카테고리를 다시 고르라고만 하지 않는가** — 홈은 히어로 +
      통계(카테고리 수/전체 건수/팀원모집 건수) + 전체 카테고리를 합친 마감임박
      상위 목록 + 카테고리 목록을 같이 보여준다. 카테고리 카드만 덩그러니 있으면
      안 된다.
- [ ] **마감 임박이 튀는가** — `--alert` pill이 다른 요소보다 먼저 눈에 들어오는가.
      화면에 마감 정보가 있는데 `--alert`를 안 썼다면 잘못된 것이다.
- [ ] **강조색이 화면당 하나인가** — `--bulb`와 `--alert`가 같은 줄에서 동시에
      "주장"하고 있으면 위계가 깨진 것. 우선순위를 다시 정한다.
- [ ] **팀원모집이 별도 서비스처럼 안 보이는가** — `--card` 배경 하나로만 구분하고,
      폰트·radius·버튼 스타일은 다른 화면과 동일해야 한다.
- [ ] **비어있는 상태(empty state)를 고려했는가** — 조건에 맞는 정보가 하나도
      없을 때 화면이 어떻게 보이는지 빠뜨리지 않는다.
- [ ] **알림/푸시를 암시하는 UI가 없는가** — 기획서에서 명시적으로 뺀 기능이다.
      "알려드릴게요" 류의 문구나 벨 아이콘을 넣지 않는다.
- [ ] **폰 프레임처럼 보이지 않는가** — 캠퍼스핏은 웹사이트다. 화면을 380~390px
      고정폭 카드(모바일 앱 목업)에 가두지 않는다. 상단 네비게이션 + 넓은 화면
      기준 레이아웃이 기본이고, 좁은 화면에서는 반응형으로 줄어드는 것이지
      "폰 안에 있는 웹앱"처럼 디자인하지 않는다. (2026-07-09, 실제 화면 리뷰에서
      "너무 앱 같다"는 피드백 이후 추가된 규칙)
- [ ] **넓은 화면에서 내용물이 빈 공간에 비해 너무 작지 않은가** — 컨테이너 폭만
      넓히고 글자·카드 크기를 그대로 두면 "앱 화면을 넓은 브라우저에 띄워놓은
      것"처럼 보인다. 실제로 겪은 재발 사례다 — 폰 프레임을 지웠는데도 여전히
      앱 같다는 피드백을 받았다. 데스크톱 뷰포트에서 실제로 얼마나 빈 공간이
      남는지 확인한다.
- [ ] **선택 가능한 요소는 선택된 상태가 눈에 보이는가** — 복수선택이 필요한 요소는
      반드시 `:checked`/hover와 구분되는 "선택됨" 스타일이 있어야 한다. 눌러도
      아무 반응이 없으면 사용자는 고장났다고 느낀다.
- [ ] **같은 진입점(카드/버튼)이 실제로 다른 결과로 이어지는가** — 카테고리 5개를
      다 눌러도 같은 화면이 나오면 안 된다. 프로토타입이라도 각 진입점은 그에
      맞는 화면/내용으로 연결한다.
- [ ] **인앱에 남는 링크와 밖으로 나가는 링크가 구분되는가** — 팀원모집만 인앱
      상세(게시판)로 가고, 나머지 일반 공고는 `row.link` + `↗` 표시로 "공식
      페이지로 나간다"는 걸 보여줘야 한다. 아무 표시 없이 눌러도 반응 없는
      행을 만들지 않는다.
- [ ] **팀원모집 글쓰기가 실제 기능으로 존재하는가** — "언젠가 만들 기능"이 아니라
      지금 화면 구성에 포함된 핵심 기능이다 (카테고리·연결 공고 선택 → 제목/내용/
      마감일 입력 → 등록). 목록만 있고 글쓰기 진입점이 빠진 채로 완성됐다고
      하지 않는다.
- [ ] **팀원모집 글이 특정 공고에 연결되어 있는가** — 카테고리 전체를 아우르는 범용
      자유게시판이면 안 된다. 링커리어도 이미 공고별 팀원모집 게시판을 갖고 있어서,
      "게시판이 있다"는 자체는 차별점이 아니다 — 필터링된 공고 안에서 바로 이어진다는
      연결이 빠지면 이 기능의 존재 이유가 없어진다.

## 새 화면을 만들 때

1. 기존 `prototype.html`의 `.topnav` + `.page` 웹사이트 레이아웃 구조를 따른다
   (radio 기반 화면 전환은 유지, 다만 폰 카드가 아니라 페이지 폭 기준).
2. 새 컴포넌트가 필요하면 먼저 `row`(`.link` 변형 포함), `post-card`, `pill`,
   `option`/`option-grid` 중 재사용 가능한 게 있는지 확인하고, 정말 새로운
   패턴일 때만 클래스를 추가한다.
3. 추가한 색·컴포넌트는 `design-tokens.css` / `design-system.md`에도 반영해서
   시스템을 갱신한다 — 프로토타입에만 있고 문서에 없는 규칙을 만들지 않는다.

## 완성 선언 전에

화면을 만들거나 고친 뒤, "다 됐다"고 말하기 전에 **처음 화면부터 끝까지 실제로 클릭해서
확인한다.** 오늘 발견된 버그(메인 화면에 뒤로가기가 빠짐, 카테고리 5개가 전부 같은 화면으로
연결됨, 체크박스가 눌러도 반응 없음)는 전부 코드를 보기만 해서는 안 보이고 **직접 눌러봐야만**
드러났다. 눈으로 코드를 읽고 "맞겠지"라고 넘어가지 않는다.

## 피드백으로 이 skill 고치기

체크리스트가 실제 판단과 안 맞으면 (예: "이 정도 경고색은 괜찮은데 왜 걸리지" 싶으면)
이 파일의 체크리스트 항목을 직접 수정한다. 규칙은 처음부터 완벽하지 않다 —
디자인 결과를 볼 때마다 "왜 마음에 안 들었는지"를 한 줄로 남겨서 항목화하는 게
이 skill을 키우는 방법이다.
